### 3.1 质控「指标配置页」写保护（不配则页面只读）

即使已执行 `10_quality_config.sql`，配置页 `/entry/quality-config` **默认仍是只读的**。
因为写接口单独加了一层保护：`config-write-ip-whitelist` 与 `config-write-token`
**两个都不配时，写请求一律 403**（刻意 fail-closed —— 改一行条件就能改全院质控口径，
而配置页与只读看板共用同一套外链鉴权，拿到链接即可改口径，风险等级不匹配）。

推荐配 IP 白名单：浏览器端零改动，只有信息科 / 质控科的指定工作站能提交保存。

```bash
# 部署目录下的 ./config/application.yml（install.sh 已自动生成；
# compose 挂载为 /app/config:ro，优先级高于 jar 内 application.yml）
zing:
  quality:
    # 逗号分隔，支持前缀匹配
    config-write-ip-whitelist: 100.120.1.104,10.0.0.
    # 这台工作站对应的责任人，记进变更历史便于追溯
    config-default-operator: 信息科-张三
```

改完 `docker compose restart zing-doctor` 生效；启动日志会打印当前写保护状态，可用于确认是否生效。

| 现象 | 原因与处理 |
|---|---|
| 页面提示「真源为 YAML，只读」 | 未执行 `10_quality_config.sql`，或配置表连不上导致自动回退 YAML（看板照常有数） |
| 页面可见但保存返回 403 | 两个写保护开关都没配 —— 最常见，按上面补一行白名单 |
| 变更历史里操作人是 `unknown` | 未配 `config-default-operator` 且外链没带 realname，事后无法追溯 |

> 也可环境变量注入：`QUALITY_CONFIG_WRITE_IP_WHITELIST` / `QUALITY_CONFIG_WRITE_TOKEN` /
> `QUALITY_CONFIG_DEFAULT_OPERATOR`。令牌方式需前端构建变量 `VITE_QUALITY_CONFIG_WRITE_TOKEN` 配合。

## 4. 一键安装部署（部署机 100.120.1.104）

交付包根目录执行 `install.sh`，**自动完成**：达梦初始化（建表+种子）→ 构建 → 启动 → 输出验证方式。

```bash
cd /opt/zing-doctor        # 部署路径 = 解压路径（脚本不写死路径）
bash install.sh
```

`install.sh` 初始化达梦时自动选择可用通道（顺序尝试）：
1. 本机 disql 客户端；
2. 达梦 Docker 容器内 disql（自动探测 dm8/dameng 容器）；
3. 本机 JDK + 内置 JDBC 初始化工具（`tools/db-init`，复用达梦驱动）。

三个通道都不可用时会打印**手动初始化指引**并退出（见 §2）。重复部署需跳过建表时可加参数：`bash install.sh --skip-db`。

> **幂等说明**：达梦初始化脚本（`00_init_user.sql` / `01_schema.sql` / `02_seed.sql`）已支持重复执行——内置 JDBC 工具（`tools/db-init`）对 `CREATE SCHEMA` / `CREATE TABLE` / `CREATE INDEX` 会先检查对象是否已存在，已存在则跳过；`02_seed.sql` 先 DELETE 再 INSERT。因此同一交付包可直接**重复运行 `./install.sh`** 完成升级/重装，不会因“对象已存在”报错中断。注意：已存在的表**不会重建**（需先 DROP 才会重建结构）。

> **老库升级（表已存在）**：`install.sh` 检测到 `sys_page_config` 已存在时跳过全量建库，自动套用 `sql/` 下的**增量脚本**（`09`~`23`，全部幂等：CREATE 与 ADD COLUMN 都先判存在），并在结束后复查关键列是否到位 —— 所以升级一般**直接重跑 `install.sh` 即可**，不必手动执行 SQL。例外两条：
> - `06_abx_drug_dict.sql` 为一次性脚本（裸 `CREATE TABLE`），不在增量清单内，从未执行过需手动执行一次；
> - `11_quality_count_rule.sql` 建表后需在看板点一次「同步指标规则」从 ICU 侧灌数。
>
> 每条脚本的作用与漏执行后果见 [DATABASE-CHANGES.md](../DATABASE-CHANGES.md)。

### 4.1 两种数据库的脚本对照

同一套库表结构有两份 SQL 实现，切换数据库后**升级用的脚本不是同一个**，切勿混用
（`sql/` 是达梦版，`sql/mysql/` 是 MySQL/MariaDB 版）：

| | 达梦 DM8（本手册） | MySQL / MariaDB |
|---|---|---|
| 安装 / 升级脚本 | `install.sh` | `install-mariadb-debian.sh` |
| SQL 目录 | `sql/` | `sql/mysql/` |
| 连接配置写在哪 | `docker-compose.yml`（`DOCTOR_URL` / `DOCTOR_USERNAME` / `DOCTOR_PASSWORD`） | `conf/db.conf`（`DB_HOST` / `DB_PORT` / `DB_ADMIN_*` / `APP_DB_*`） |
| Spring profile | `dm`（默认，不用改） | `mariadb` / `mysql`（脚本连上后按 `VERSION()` 自动写入） |
| 每次升级是否全量重跑脚本 | **否**：先探测 `sys_page_config`，已存在则跳过全量、只跑增量清单 | **是**：`MAIN_SQL` 里的脚本每次全跑，靠脚本自身幂等 |
| 新增脚本要登记几处清单 | **3 处**（`FULL_SQL` / `FULL_SQL_JDBC` / `INCREMENTAL_SQL`） | **1 处**（`MAIN_SQL`） |
| 跳过 SQL 的参数 | `--skip-db` | `--config-only` |
| 升级后的重启方式 | `docker compose up -d --build`（脚本内部完成） | `systemctl restart zing-doctor` |
| 备份方式 | `dexp` 或 DBA 侧模式备份 | `mysqldump` / `mariadb-dump` |

两侧共用一份 DATABASE-CHANGES.md。**新增脚本必须两边同时落地**，详见其「双数据库：脚本归属与新增脚本四步规则」一节。

### 4.2 升级（同结构换版本）

按「这次有没有改表结构」选，不要凭习惯：

| 场景 | 动作 | 命令 |
|---|---|---|
| **只换程序**（只更新 jar / 前端，无结构变更） | 覆盖产物后跳过建库 | `cp -r <新包>/frontend/dist/. /opt/zing-doctor/frontend/dist/`<br>`cp <新包>/app/zing-doctor.jar /opt/zing-doctor/app/`<br>`bash install.sh --skip-db` |
| **含表/字段变更**（最常见，跟着 DATABASE-CHANGES 走） | 直接重跑，脚本自己判断新库 / 老库 | `bash install.sh` |
| **只改达梦地址或账号** | 改 compose 后跳过建库 | `vi docker-compose.yml` → `bash install.sh --skip-db` |
| **全新安装** | 检测到库为空，自动走全量初始化 | `bash install.sh` |

> ⚠️ 三点最容易踩：
> 1. **只换 jar、不跑 `install.sh`** —— 历史上现场漏列的主因（`15_quality_patient_fields.sql` 就这样缺席过，表现是质控配置页打开即 500）。
> 2. **前端 `frontend/dist` 不能 `rm -rf`**：它以 bind mount 挂进 nginx 容器，删掉重建会换 inode，容器仍指向旧目录（脚本检测到 `dist/index.html` 缺失会直接中止部署）；只能用 `cp -r <新包>/frontend/dist/. <目标>/frontend/dist/` 覆盖。
> 3. **初始化通道三选一**（本机 disql / 达梦容器内 disql / JDK + DbInit），全不命中时脚本会打印手工指引并退出，此时按 §2 手工执行。

### 部署模式自动切换（关键）

`install.sh` 建表完成后会自动探测服务器能否访问 Docker Hub：

| 探测结果 | 部署模式 | 说明 |
|---|---|---|
| **能访问 Docker Hub** | Docker Compose 全量 | `backend` + `frontend` 两个容器，正常构建镜像 |
| **无法访问（内网）** | **内网直连** | 后端用服务器自带 Java 8 直接 `java -jar app/zing-doctor.jar`；前端复用服务器已有 `nginx:stable` 镜像托管静态页。**不拉取任何外网镜像** |

内网直连模式下：
- 后端以 `ICU_DATA_PROVIDER=sql` 启动（连接真实 ICU 库），进程号写入 `backend.pid`，日志在 `logs/backend.log`
- 前端容器 `zing-doctor-frontend` 映射 `2001:80`，自动生成 nginx 反代配置（`/api`、`/entry` 转发到本机 `8081`）
- 重复部署会自动停旧进程/容器再启动

> 本手册配套交付包已内置 `app/zing-doctor.jar`（后端可执行包）与两个架构的 docker-compose 二进制，内网服务器无需联网即可完成部署。

等待构建完成后查看状态：

```bash
docker compose ps              # backend/frontend 都应为 Up
docker logs zing-doctor-backend --tail 50   # 确认 Started ZingDoctorApplication
```

## 6. ICU 系统外链对接（联调）

1. 页面编码已注册（共 14 个，完整清单见 `docs/02-外链传参规范.md` §1），常用例如：
   - `abx-patient-list` → 疑似感染患者列表（无需业务参数）

2. 签名：HMAC-SHA256，密钥 = 医生决策系统 `EXTERNAL_LINK_SECRET`，规范见 `docs/02-外链传参规范.md`。
3. 外链地址：`http://100.120.1.104:2001/entry/abx-decision?expire=..&sign=..&patientId=..`
4. ICU 侧实现：按规范自行签名，或调用医生决策系统 `POST /api/external/token` 签发。
5. 首次联调用 curl 直接打开外链 URL 验证，再接入 ICU 系统内跳转。

## 8. 常见问题

| 现象 | 原因与处理 |
|---|---|
| ICU 表不存在 | 模式名/表名大小写：本 SQL 用 `"zing_icu_db_prod"."patient_info"`（小写）。已确认模式存在；若具体表名大小写不同，按实库调整。验证：`SELECT TABLE_NAME FROM ALL_TABLES WHERE OWNER='ZING_ICU_DB_PROD';` |
| 列表为空（sql 模式） | ① 确认 `patient_info` 有 `is_in_depart=1` 的在科患者；② 任一筛选条件命中。验证：`SELECT COUNT(*) FROM "zing_icu_db_prod"."patient_info" WHERE is_in_depart=1;` |
