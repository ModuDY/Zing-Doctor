# 营养支持分析：数据盘点与实施方案

> **版本：v1.0（待重症库实测后定稿）**  
> **更新日期：2026-10-13**  
> **状态：数据核查任务 + 产品/技术初稿**  
> **用途：交给可连接 ICU 数据库的 AI/工程人员执行只读数据盘点，并据实补齐实施方案。**

---

## 0. 本文目的与当前结论

本方案定义一个独立的 **「营养支持分析」** 页面。它不合并进患者诊疗摘要，也不把营养、出入量、体温等所有趋势塞到同一页面。页面目标是帮助医生追溯患者的营养支持医嘱、实际执行记录和可核实的营养摄入信息。

项目代码和现有数据文档能够确认：

- ICU 库存在医嘱执行主表 `patient_advice_execute`、执行明细 `patient_advice_execute_item`、医嘱药品明细 `patient_advice_execute_drug`、执行调速记录 `patient_advice_execute_step`；
- 项目已有代码通过 `patient_advice_execute` + `patient_advice_execute_item` 获取按小时执行记录，字段包括 `execute_hour`、`amount`；另有 `is_to_io='1'` 的药品执行入量汇总逻辑；
- ICU 库有出入量记录和项目配置，现有代码可依据 `config_io_item.io_type='o'` 识别出量，尿量项目编码为 `ii_nl`；
- `patient_info.weight/height` 为文本字段，历史盘点中存在非数值值，使用前必须校验数值、单位和采集时间；
- 当前仓库没有已经落地的独立营养分析模块，也没有文档证明“营养产品的实际执行量、能量/蛋白成分、营养目标”在生产数据中完整可用。

因此当前只能得出：**医嘱执行数据源存在，营养实际摄入量是否可计算尚待生产库核实。** 医嘱执行表有记录，不等于这些记录就是肠内/肠外营养；`amount`、输液量或出入量也不能直接换算为热量/蛋白质。本文后续的功能承诺需由数据盘点结果决定。

## 1. 产品定位与范围

### 1.1 独立菜单与页面

建议新增独立菜单 **「营养支持分析」**，可从患者工作台患者行的操作入口进入，页面接收当前患者上下文；不把营养趋势并入摘要卡片，不新建第二份患者选择器。

菜单页面承担：

1. 营养支持医嘱回顾；
2. 实际执行/给入记录核查；
3. 若制剂成分与执行量经过验证，展示能量、蛋白质等摄入趋势；
4. 若营养处方目标、患者体重等条件可靠且临床口径获批，再展示目标对照。

### 1.2 一期不做的事

- 不把“开立医嘱”显示成“已经摄入”；
- 不把“已执行”自动解释为完整输注/完整喂养；
- 不从产品名称猜测配方、热量或蛋白质含量；
- 不将计划量、实际给入量和患者吸收量混为一谈；
- 不在缺体重、身高、目标公式、营养成分时计算达标率；
- 不自动给出营养处方、医嘱建议或临床诊断；
- 不把出入量总量直接当作肠内/肠外营养摄入。

## 2. 数据盘点任务：交给连库人员/AI 的工作清单

### 2.1 数据库与范围确认

开始查询前先记录：

- 实际连接实例类型和版本：达梦、MariaDB 或其他；
- ICU 业务 schema 名、当前项目使用的数据源配置别名；
- 查询日期、数据库时区、业务时区；
- 只读账号是否确认为只读；
- 统计时间窗：优先近 90 天，并补充近 12 个月聚合分布；
- 以 `patient_id`、`in_hospital_no` 还是 `execute_id` 为主关联键，核实一次住院/重复入科关系。

仓库中的数据库文档和运行环境可能不是同一时点或同一数据库产品。应先检查实际连接的 schema/表/列，再运行与当前方言匹配的 SQL；不要把旧盘点行数当作生产实时结果。

### 2.2 需要检查的表和字段

优先检查下列数据源；发现其他营养相关表时一并登记，但先确认字段语义和数据量。

| 数据层 | 表/候选表 | 重点核实字段/语义 |
|---|---|---|
| 患者 | `patient_info` | `id`、`in_hospital_no`、入/出科时间、`is_in_depart`、`weight`、`height`、性别、年龄；体重/身高是否数值、单位、采集时间和历史变化 |
| 医嘱原始 | `patient_original_advice`、`patient_advice` | 医嘱名称、类型、频次、途径、计划剂量/速度、开立/停止时间、撤销状态；识别肠内、肠外、口服补充、普通液体、药物及其他营养相关医嘱 |
| 医嘱执行主表 | `patient_advice_execute` | `id`、`patient_id`、`in_hospital_no`、`name`、`advice_type`、`drug_method_name`、`freq_name`、`start_time`、`end_time`、`plan_start_time`、`status`、`is_to_io`、`liquid_amount`、`drug_now_speed`、速度单位、删除/有效标记 |
| 医嘱执行小时明细 | `patient_advice_execute_item` | `execute_id`、`patient_id`、`execute_hour`、`amount`、剂量/单位、记录是否是实际执行而非计划 |
| 医嘱执行药品明细 | `patient_advice_execute_drug` | `execute_id`、`drug_name`、`drug_dose`、剂量单位、规格、药品自身液量；区分配方成分和溶媒 |
| 执行步骤/调速 | `patient_advice_execute_step` | `execute_id`、`step_time`、`step_type_name`、`speed`、暂停/恢复/执行语义；能否重建历史给入量 |
| 出入量 | `patient_io_module_item_record`、`patient_io_module_item`、`config_io_item` | 项目名称、编码、`io_type`、`item_value`、单位、时间、记录状态；哪些项目是真实肠内喂养/营养液给入，哪些只是普通入量 |
| 护理措施/喂养记录 | `patient_measure_module_item_record` 及其配置表 | 是否有鼻饲/肠内营养/胃残余量/暂停喂养/实际泵入量等结构化数据，频率和撤销口径 |
| 药品/产品目录 | `config_drug`、药品字典、耗材/营养制剂字典 | 商品码、通用名、规格、单位、浓度、每 100ml 能量、蛋白/脂肪/碳水等营养成分是否存在且权威 |
| 其他 | 表名待发现 | 营养评估、营养处方、营养会诊、能量目标、蛋白目标、肠内泵、TPN 配方等数据是否存在 |

### 2.3 必须回答的业务问题

数据报告必须明确回答，而不是只给出表行数：

1. 医嘱名称/商品名称中实际有哪些肠内营养、肠外营养、营养补充制剂和途径？请列名称及编码的**去标识化聚合频数**。
2. 这些记录中，哪些是开立计划，哪些有执行状态，哪些存在按小时的实际执行明细？
3. `patient_advice_execute_item.amount` 的确切业务含义、计量单位和记录粒度是什么？它是每小时实给量、一次执行量、计划量还是其他？需要用表注释、程序逻辑、执行样例和 ICU 厂商/业务人员交叉验证。
4. 对肠内营养、肠外营养，是否能按执行记录还原每个时间段真实给入体积？暂停、速度调整、补录、退执行、跨小时、跨日和医嘱结束如何表示？
5. `is_to_io='1'` 的 `patient_advice_execute` 代表哪些药物/液体？营养制剂是否包括在内？如包含，是否会与 I/O 记录重复计量？
6. I/O 模块的“入量”是否记录肠内营养实际给入？是否包含冲管水、药物、静脉液体和输血？能否拆分？
7. 制剂营养成分来自什么表或院内维护资料？是商品规格、每袋、每 100ml 还是配方级？是否存在生效日期、批次差异和稀释液？
8. 患者体重/身高是否有历史记录和测量时间？目前患者主表值能否代表营养计算时点？是否有“卧床”等非数值文本？
9. 营养目标/处方目标是否结构化存储？若只有医生自由文本，不应自动提取为正式目标。
10. 近 90 天及近 12 个月分别有多少患者具有：营养医嘱、执行记录、可识别实际量、可映射制剂成分、可计算能量、可计算蛋白质、有效体重、明确目标？给出逐层漏斗和分母。
11. 同一患者同一时点出现多个执行来源时，如何去重并避免“医嘱执行量 + I/O 入量”双重累计？
12. 在数据库不可达或记录为空时，如何区分 `NOT_RECORDED` 和 `UNKNOWN`？

### 2.4 结果交付格式

请交付一份“数据盘点附录”，建议文件名：`docs/24-营养支持分析-生产库数据核查结果.md`，内容包括：

- 实际数据库/schema/核查时间/时间窗；不得记录账号、密码或连接密钥；
- 表结构摘要、字段业务含义、关联键、软删除/有效状态；
- 候选医嘱与营养项目字典（编码、名称、分类依据、确认人/状态）；
- 数据量与覆盖漏斗：记录数、去重患者数、去重住院 episode 数，明确统计日期和过滤条件；
- 计划医嘱、实际执行、实际给入、制剂成分、营养目标分别有无数据；
- 单位、时间语义、重复/撤销/暂停/补录问题及其证据；
- 至少 3 个去标识化案例：仅给伪造/脱敏编号和结构化摘要，不含姓名、完整住院号或可识别自由文本；
- 建议一期可实现范围、不能实现范围、待 ICU/临床确认事项；
- 所有 SQL（或关键 SQL 片段）及耗时/执行计划摘要；禁止保存生产敏感数据明细。

## 3. 只读 SQL 盘点草案

以下是探查方向，不是可直接照搬的最终 SQL。先核实数据库方言、字段类型和索引；仅使用只读查询、有限时间窗、聚合结果和样例上限。不要 `UPDATE/INSERT/DELETE/DDL`，不要 `SELECT *` 拉取生产全量数据。

### 3.1 表名发现

按实际数据库使用数据字典检索表名中的 `advice`、`nutrition`、`enteral`、`parenteral`、`feed`、`diet`、`io`、`measure` 等关键词；逐表读取列名、类型、注释、索引。DM 使用 `ALL_TABLES` / `ALL_TAB_COLUMNS`；MariaDB 使用 `information_schema.tables` / `information_schema.columns`。不要因为表存在就认定已启用，需另查有效数据量和最近时间。

### 3.2 医嘱名称与状态分布

先按限定时间窗聚合医嘱名称、类型、用法、状态、途径和是否计入 I/O，结果只返回 TOP 若干个类别；再由临床/营养师确认词典分类。名称关键词只用于发现候选，不作为唯一分类逻辑。

伪 SQL：

```sql
SELECT name, advice_type, drug_method_name, status, is_to_io, COUNT(*) AS record_count
FROM patient_advice_execute
WHERE del_flag = 0
  AND COALESCE(start_time, plan_start_time) >= :start_time
  AND COALESCE(start_time, plan_start_time) <  :end_time
  AND (name LIKE '%营养%' OR name LIKE '%鼻饲%' OR name LIKE '%肠内%'
       OR name LIKE '%肠外%' OR name LIKE '%全营养%' OR name LIKE '%氨基酸%'
       OR name LIKE '%脂肪乳%' OR name LIKE '%能全力%' OR name LIKE '%瑞能%')
GROUP BY name, advice_type, drug_method_name, status, is_to_io;
```

> `COALESCE`、日期类型和分页写法须按真实数据库方言调整。若名称字段没有规范营养标识，应扩大为只在患者键/时间索引范围内的名称分布抽样，不要对全表无界 `LIKE`。

### 3.3 执行明细与单位分布

从识别出的有限 `execute_id` 集合关联 `patient_advice_execute_item`、`patient_advice_execute_drug`、`patient_advice_execute_step`，统计：

- 主表到明细的关联成功率；
- 有小时执行明细、无明细、有调速步骤的记录数量；
- `amount`、剂量、速度字段的单位和空值率；
- `status`、`step_type_name` 的取值分布；
- 小时记录重复、负值、超范围值、相同执行 ID 多来源重复等质量问题。

示例连接关系先按项目代码核实：`patient_advice_execute.id = patient_advice_execute_item.execute_id`，但要继续确认明细 `patient_id` 是否一致、删除状态字段、执行时间边界和 status 语义。

### 3.4 I/O 和实际给入记录

在限定患者集合和日期范围内，查询 I/O 配置表中 `io_type`、项目名、项目编码、单位分布；再以项目编码联结记录表，统计覆盖患者数、记录频次和时间范围。需要识别哪些是营养给入、冲管水、药物/静脉液体、其他入量、出量，不能把所有 `io_type='i'` 归为营养。

### 3.5 覆盖漏斗与分母

建议按 ICU 在科/出科 episode 作为统计基础，并解释去重键。漏斗至少包括：

```text
符合纳入范围患者/episode
  → 命中候选营养支持医嘱
  → 有实际执行明细
  → 可确认执行量单位和时间语义
  → 可映射到已核验的营养制剂
  → 制剂营养成分完整
  → 患者有效体重可用
  → 存在经确认的目标口径
  → 可计算能量/蛋白摄入及目标差值
```

每层同时报患者数、episode 数、记录数和占上层比例；空数据表示“无记录/未启用”而非 0 摄入。

## 4. 数据核验后的功能分级

根据连库结果选择实际交付级别，不预设一定能达到最高级。

### Level 0：数据不足

仅返回数据源核查结果和不足项，不上线患者营养趋势；不做空壳菜单或模拟真实病人营养值。

### Level 1：营养支持医嘱回顾

适用条件：能可靠识别营养支持相关医嘱，并可显示医嘱状态/时间/途径，但实际执行量或成分不完整。

可展示：计划医嘱、开立时间、途径/频次、执行状态、暂停/结束记录、原始医嘱名称；明确标注“计划/医嘱信息，不代表实际摄入”。

### Level 2：实际执行量/给入量回顾

适用条件：执行明细可证实是实际给入量，单位和执行时间明确，暂停/调速/撤销能正确处理，且来源间可去重。

可展示：计划量与执行量并列、每小时/每日实际给入体积、未执行/暂停/缺记录区间、数据覆盖率。未完成单位和状态核实前，不显示累计“实际摄入”。

### Level 3：能量与蛋白质估算

仅当制剂识别和营养成分表权威、有效期清楚，且实际执行量可追溯时启用。

```text
估算摄入量 = 已确认产品成分 × 已确认实际给入量
```

肠内营养和肠外营养分开展示；复合配方、稀释、剩余/弃置、未完成输注、多个产品混合及冲管量均需按营养科确认规则处理。吸收量不由医嘱或执行数据推算。

### Level 4：目标达成分析

只有当临床确认目标计算标准、有效体重/身高来源和测量时间，且营养处方目标可追溯时才启用。目标可来自经确认的处方，也可来自经医院批准的计算规则；页面显示目标来源和计算依据。不得直接把固定 kcal/kg 或蛋白 g/kg 常数写成默认诊疗建议。

## 5. 页面设计草案

### 5.1 顶部患者与时间范围

- 患者床号、姓名（遵从权限）、住院号、ICU episode、当前状态；
- 时间范围：24 小时、72 小时、7 天、自定义；默认 7 天；
- 显示数据更新时间、来源覆盖区间和数据完整性提示；
- 患者身份优先使用 `patient_id + in_hospital_no/episode` 校验，防止同一患者多次住院记录混用。

### 5.2 摘要指标（仅显示数据足够的指标）

- 营养支持类型：肠内 / 肠外 / 联合 / 未识别；
- 当前医嘱状态和最后执行时间；
- 计划量、实际执行量（Level 2 起）；
- 估算能量、蛋白质（Level 3 起）；
- 目标与达标比例（Level 4 起）；
- 当前体重、来源时间和是否有效（计算需要时）；
- 每项都带状态：已取得、部分可得、未记录、不适用、查询未知。

### 5.3 趋势图

- 计划量和实际执行量使用不同线型；
- 能量、蛋白质如可计算则单独图层/独立图，不把不同单位混在同一轴；
- 暂停、撤销、换制剂、调速以事件标记显示；
- 计划与执行差值只作事实展示，不自动评价“营养不足/过量”；
- 按天聚合前保留原始小时明细入口；缺失区间显示断点或阴影，不插值补零。

### 5.4 明细表

建议列：时间、营养方式、产品/医嘱原名、计划量、实际执行/给入量、单位、执行状态、来源表、解析/映射状态、备注。支持查看原始来源记录，敏感字段按权限处理。

## 6. 接口和数据模型草案

### 6.1 查询接口（最终以数据盘点和现有 API 风格调整）

```text
GET /api/nutrition/patient/{patientId}/analysis
    ?inHospitalNo=&startTime=&endTime=

GET /api/nutrition/patient/{patientId}/orders
    ?inHospitalNo=&startTime=&endTime=

GET /api/nutrition/patient/{patientId}/trend
    ?inHospitalNo=&startTime=&endTime=&granularity=HOUR|DAY
```

所有接口须校验当前用户科室权限；外链继续验证来源系统授权范围。不得仅信任 URL 的患者 ID 或住院号。

### 6.2 DTO 状态字段

建议响应对每类数据分别返回：

```json
{
  "dataStatus": "FOUND | PARTIAL | NOT_RECORDED | NOT_APPLICABLE | UNKNOWN",
  "source": "实际表/逻辑数据源",
  "window": {"startTime": "...", "endTime": "..."},
  "unit": "...",
  "lastUpdatedAt": "...",
  "qualityNotes": [],
  "records": []
}
```

`UNKNOWN` 表示查询失败/权限不确定/来源异常；`NOT_RECORDED` 表示成功查询但无记录。不能将二者混成 0。

## 7. 安全、性能与审计要求

- ICU 只读数据源；营养模块第一版不写回 ICU 数据库、不自动开立或修改医嘱；
- 大表查询先用患者集合/住院号/时间索引限制范围，禁止全院 `LIKE` 扫描；
- 先批量查询后按患者/执行单分组，禁止一患者一 SQL；单患者查询必须限制最大时间窗和返回条数；
- 防止执行主表、小时明细、药品明细和 I/O 记录多对多 JOIN 后重复累计；先按逻辑主键去重再汇总；
- 原始数据保留来源表、主键、原值、单位、执行时间、状态；聚合值可下钻；
- 日/小时边界统一采用左闭右开 `[start, end)`；时区和自然日切分明确；
- 数据无权访问、接口失败、解析失败分别记录错误状态，不默认为 0；
- 生产库盘点报告不得输出姓名、完整住院号、可识别备注、账号密码、token 或连接串。

## 8. 临床与工程验收

### 数据验收

- 医嘱、执行记录、I/O 记录三者能区分并可追溯；
- 执行量单位、时间含义、status 含义由重症系统业务方确认；
- 营养产品的成分/规格有权威来源和生效时间；
- 计划量与实际量不重复；执行量和 I/O 量不双计；暂停和调速计算可复算；
- 体重/身高的数值、单位、测量时间经过验证；
- 覆盖率和不可计算比例可见，不用全院平均掩盖个体缺失。

### 临床验收

- 营养师/ICU 医生确认产品分类、能量/蛋白质换算、目标来源与评价文案；
- 用户能看出医嘱/计划、实际执行、估算摄入和吸收之间的边界；
- 数据不足时展示明确缺项，不给出虚假的达标率或治疗建议；
- 营养目标及阈值未获批前不做自动预警。

### 工程验收

- 科室权限、历史患者、外链访问通过测试；
- SQL 执行计划/耗时符合要求，无 N+1；
- 单元测试覆盖重复执行记录、单位变化、无效体重、暂停/调速、跨日、时间缺失、产品未映射、查询失败；
- 主要图表每个点可追溯到原始数据；
- 至少用去标识化真实样例和合成边界用例验收，不在生产数据上写测试记录。
