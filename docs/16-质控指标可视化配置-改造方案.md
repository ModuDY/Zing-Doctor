> 目标读者：后端 / 前端开发、质控科业务方、评审人
> 关联文档：`15-质控指标中台-产品设计.md`（现有实现）、`02-外链传参规范.md`（鉴权与页面注册）

> 本文档第五～七章为设计说明，实际交付范围以 §七 分期表的「状态」列与 §八 迁移步骤为准。

## 一、为什么要改

需求很直接：**质控科的人希望在页面上调整指标口径，不想每次都找开发改文件、改完还要重启**。

但现有架构做不到，卡在四个硬约束上：

| # | 约束 | 证据 | 后果 |
|---|---|---|---|
| 1 | 表达式只存在 YAML 里 | `quality/metrics/*.yaml` 由 `QualityDslLoader` 从 **classpath** 读取 | jar 部署**无法写 classpath**，页面上改不了 |
| 2 | 字典表不存表达式 | `quality_index` 建表只有展示字段（编号/名称/单位/值类型…），**没有** `where` / 分子 / 分母 列 | 页面**没有数据可编辑**，字典表只是展示副本 |
| 3 | 引擎只认内存 DSL | `QualityEngine` 依赖 `QualityDslLoader.getFacts()` / `getMetrics()` | 改 DB 不会影响计算 |
| 4 | `reload()` 无人调用 | 全仓仅 `QualityDslLoader.init()`（启动时）调用一次 | **「改配置即热生效」不成立**，实际必须重启 |

> 约束 4 是本次排查中发现的既有缺陷：`QualityIndexSyncService.sync()` 只把**内存中已加载**的配置写进字典表，从不重读文件。因此文档中「改完 YAML 点同步即热生效」的说法一直是失效的。**该缺陷已在本次改造中先行修复**（见第二部分）。

结论：要做可视化配置，必须**把配置真源搬到 DB，并让引擎从 DB 加载**。

## 二、已落地：热生效修复（先行交付）

这部分改动小、风险低、收益立竿见影，因此先于可视化编辑独立交付。

### 2.1 补上 `reload()` 调用

新增 `QualityIndexSyncService.reloadAndSync()`，「同步字典」按钮从「只落库」变为「**重读配置 + 落库**」：

```java
public int reloadAndSync() {
    dsl.reload();   // 先重读配置文件
    return sync();  // 再落库
}
```

`QualityController.syncIndex()` 改调该方法。启动路径仍用 `sync()`，避免启动时重复读文件。

### 2.2 `reload()` 改为原子替换

原实现的第一行就把新数据源赋给了 `this.sourceConfig`，后续事实层/指标层解析若抛异常，内存里会残留「**新数据源 + 旧事实层**」的错配。运行期反复热加载时这会导致难以排查的诡异结果。

改为三层全部在局部变量中解析完成后**一次性赋值**，实现「要么整体换新、要么保持全旧」。

### 2.3 新增外部配置目录（`zing.quality.config-dir`）

**这是让热生效真正可用的前提**：jar 内的 classpath 资源运行时不可写，若不把配置放到 jar 外部，`reload()` 重读到的仍是打包时的旧文件。

```yaml
zing:
  quality:
    # 留空 = 只用 jar 内打包配置（行为与改造前完全一致）
    config-dir: /data/zing-doctor/config/quality
```

读取规则为「外部优先、缺失回退 classpath」，且**整体覆盖、不做逐文件合并**（避免外部目录只放一半导致事实层与指标层来源错配）：

```
{config-dir}/sources.yaml      → 该文件存在时生效
{config-dir}/facts/*.yaml      → 目录存在且含 yaml 时生效（整体覆盖）
{config-dir}/metrics/*.yaml    → 同上
```

改造后「改配置 → 点同步字典」即可生效，无需重启。

> 部署动作：把 `src/main/resources/quality/` 整体复制到 `/data/zing-doctor/config/quality/`，并在配置里指向它。不配置 `config-dir` 时行为不变，可安全先上线再启用。

## 三、核心决策：真源切到 DB，引擎零改动

关键判断：`FactDefinition` / `MetricDefinition` 是纯 POJO，字段与 YAML 一一对应。只要 DB 表能还原成这两个对象，**`SqlCompiler` 和 `QualityEngine` 一行都不用改**。

```
新增：quality_metric_def / quality_fact_def（DB 真源）
        ↓ QualityConfigRepository（CLOB-JSON ↔ POJO）
QualityDslLoader.reload()  ← 唯一改动点（加一个分支）
        ↓ 内存 factMap / metricMap（结构不变）
SqlCompiler / QualityEngine / QualityCalcService  ← 零改动
```

- 开关：`zing.quality.config-source: yaml | db`，**默认 `yaml` 保持向后兼容**
- YAML 降级为「出厂种子」：DB 配置表为空时自动导入一次
- **数据源层（`sources.yaml`）不开放编辑**：它只声明物理表名，改错会导致整个域查不到数据，且一年也改不了几次，保持 YAML 管理、页面只读展示

## 五、后端改造

### 5.1 新增 `QualityConfigRepository`

负责 DB ↔ POJO 转换，复用现有 `ObjectMapper` 处理 CLOB-JSON。

```java
List<MetricDefinition> loadMetrics();   // status=1
List<FactDefinition>   loadFacts();
```

### 5.2 改造 `QualityDslLoader.reload()`（唯一侵入点）

```java
public synchronized void reload() {
    // 数据源层仍走 YAML
    this.sourceConfig = readOne(props.getSourceLocation());

    List<FactDefinition>   facts;
    List<MetricDefinition> metrics;
    if ("db".equalsIgnoreCase(props.getConfigSource())) {
        if (configRepo.isEmpty()) { seedFromYaml(); }   // 出厂种子，只导一次
        facts   = configRepo.loadFacts();
        metrics = configRepo.loadMetrics();
    } else {
        facts   = readYamlFacts();
        metrics = readYamlMetrics();
    }
    // 重建 factMap / metricMap，volatile 原子替换（与现有实现一致）
}
```

### 5.3 新增 `QualityConfigService`（写侧）

保存流程：**校验 → 落库 → 写历史 → reload → 热生效**

```java
ValidateResult   validateMetric(MetricDefinition m);  // 只校验，不落库
MetricDefinition saveMetric(MetricDefinition m, String operator);
void             disableMetric(String code, String operator);
void             rollback(String defType, String defKey, int exprVersion, String operator);
```

改表达式时**自动 `expr_version + 1`** —— 用户不必记着手动升版本，这是最容易忘、后果最严重（历史值口径无法回溯）的动作。

### 5.4 校验链（成败关键，四级）

裸 SQL 片段让业务人员手输，不校验必然出事。逐级拦截：

| 级别 | 内容 | 手段 | 挡住什么 |
|---|---|---|---|
| **L1 安全** | 抽现有 `QualityEngine.guard()` 为公共 `SqlFragmentValidator` 并**大幅加强** | 见下 | 注入、多语句、DDL/DML |
| **L2 编译** | 调 `SqlCompiler.compileMetric()` | 捕获异常 | 表达式结构性错误 |
| **L3 字段** | 解析事实层 `derive` 的 `AS xxx` 别名集合，校验指标引用的列都在集合内 | 纯内存，毫秒级 | 引用不存在的列（最高频错误） |
| **L4 试跑** | `SELECT * FROM (编译SQL) x WHERE 1=0` | `sqlMapper.query()` | 表名/列名/函数/方言错误 |

**L1 必须加强** —— 现有 `guard()` 只拦 `;` `--` `/*`，且运行期不再有「配置由开发评审」这层人工兜底：

```java
private static final Pattern DML_DDL = Pattern.compile(
    "\\b(insert|update|delete|drop|truncate|alter|create|grant|revoke|merge|exec|execute|call|commit|rollback)\\b",
    Pattern.CASE_INSENSITIVE);
private static final int MAX_LEN = 4000;
// 规则：① 禁语句分隔/注释 ② 禁 DML/DDL 关键字 ③ 禁长度超限
```

**L4 是性价比最高的一道**：达梦在解析期就校验表名/列名/函数/方言，一次 `WHERE 1=0` 能把约 90% 的编辑错误在执行前拦下，且几乎不耗资源。

### 5.5 接口清单

全部挂在 `/api/quality/config/**`，复用现有外链鉴权头（`X-External-PageCode` / `X-External-Token`）。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/metrics` | 指标配置列表（含表达式，按域/关键字过滤） |
| GET | `/metric/{code}` | 单条详情 |
| POST | `/metric/validate` | **只校验不保存**：返回编译 SQL + 试跑结果 + 错误定位 |
| POST | `/metric` | 保存（新增/更新）→ 升版本 + 写历史 + reload |
| POST | `/metric/disable` | 停用（不物理删） |
| GET | `/facts` `/fact/{name}` | 事实层配置 |
| POST | `/fact/validate` `/fact` | 事实层校验 / 保存 |
| GET | `/history` `/history/detail` | 变更历史 / 某版本快照 |
| POST | `/rollback` | 回滚到指定版本 |
| **GET** | **`/fields?fact=xxx`** | **事实层可选列**（derive 解析出的列名） |
| GET | `/impact?fact=xxx` | **影响面**：改这个事实层会影响哪些指标 |
| GET | `/enums` | 域 / 值类型 / 聚合方式 / 实现状态枚举 |
| GET | `/status` | 真源 + **写权限**（`writeAllowed` / `writeHint`）+ 当前操作人 |
| GET | `/metrics/export` | **导出**生效口径的完整 JSON（含表达式正文） |
| POST | `/metrics/import` | **批量导入**（逐条校验、逐条落库，部分成功语义） |

`/fields` 与 `/impact` 是两个关键接口：

- `/fields` 让前端能做**字段选择器**，而不是让用户盲写列名 —— 直接把 L3 类错误消灭在输入阶段
- `/impact` 在改事实层前告知「该改动影响本域 46 条指标」，避免改一条崩一片

### 5.6 权限（已落地：写接口与只读接口分开鉴权）

配置写接口与查询接口**分开鉴权**。原设计只写了「建议加白名单」，实现时明确了机制与兜底策略，
落在 `QualityConfigGuard` + `QualityConfigWriteInterceptor`（注册于 `WebConfig`，路径 `/api/quality/config/**`）。

**为什么必须单独做**：改一行条件就能改全院质控口径，而配置页与只读看板共用同一套外链鉴权 ——
拿到外链（ICU 模板里写死的 `extToken`）即可改生产口径，风险等级明显不匹配。

| 机制 | 配置项 | 说明 |
|---|---|---|
| IP 白名单（**推荐**） | `zing.quality.config-write-ip-whitelist` | 逗号分隔，元素支持**前缀匹配**（`10.0.0.` 覆盖整段）。浏览器端零改动、无需重建前端 |
| 写接口令牌 | `zing.quality.config-write-token` | 写请求须带 `X-Quality-Config-Token`；常量时间比较，避免时序侧信道 |
| 两者都配 | — | **都必须通过** |
| **两者都不配** | — | **写接口一律 403（fail-closed）** |

兜底策略是刻意选的：宁可让部署方显式开一次口子，也不要默认放开一个能改生产口径的入口。
启动日志会打印当前写保护状态，便于确认是否生效。

几条边界约定：

- **只拦写、不拦读**：GET/HEAD/OPTIONS 直接放行，避免配置失误把只读看板一起打挂；
- **取 `X-Forwarded-For` 第一段**判 IP：有 Nginx 时 `getRemoteAddr()` 是代理地址，直接用它会让白名单「全放行」或「全拒绝」；
- **操作人一律由服务端解析**（`X-Operator` 头 → 外链 `realname` → `username` → `userId` → `unknown`），
  **不再接受前端传的 `operator` 参数** —— 那等于让审计字段由被审计者自己填写。取值会去换行并截断到 64 字符（审计列长）；
- 页面通过 `/status` 的 `writeAllowed` / `writeHint` **一进来就知道能不能改**，避免编辑半天、点保存才收到 403；
- 归属说明：这层是**访问控制**，操作人解析是**审计归属，不是身份认证**（外链参数与请求头均可伪造，
  真正的兜底是访问控制本身）。接入 SSO 后应整体替换为角色判定 —— 与本项目「待接 SSO」是同一个缺口。

### 5.7 批量导入 / 导出

`GET /metrics/export` + `POST /metrics/import`，载荷都是 `MetricDefinition` 列表，因此**导出文件可直接回灌**。
这条路径本身就是跨环境迁移手段：测试环境用 YAML 调好口径 → 导出 → 生产导入，不必手工敲 SQL。

导出取的是内存中的**生效配置**（`QualityDslLoader.sortedMetrics()`），因此 yaml 真源下同样可用；
与列表接口的关键差别是**不清空表达式正文**（列表接口会清空，否则一次返回 127 条完整 SQL 太重）。

导入的三条刻意设计：

1. **逐条校验、逐条落库，不用整体事务** —— 上百条里有 2~3 条写错是常态，整体回滚会让人只能「全部重来」；
   接口返回逐条结论（`CREATED / UPDATED / SKIPPED / FAILED` + 原因），好的进去、坏的带着原因留下。
2. **复用单条保存的校验链** —— 否则导入就成了绕过 L1–L4 护栏的后门。
3. **全部处理完只热生效一次** —— 逐条 `reload()` 会重放 127 条口径，导入 100 条就是 100 次全量重载。

其他约定：默认 `mode=skip`（同编号只跳过、不覆盖），覆盖需显式选择并二次确认；
单次上限 500 条；批量默认 `trial=false`（逐条真跑会让页面长时间无响应，试跑留给单条编辑）；
批内编号重复只处理首次出现。

### 6.2 关键 UX：双层编辑模式

这是**控制风险的核心设计**：

| 模式 | 面向 | 交互 | 风险 |
|---|---|---|---|
| **简单模式**（默认） | 质控/业务人员 | 字段下拉（来自 `/fields`）+ 操作符 + 值 + AND/OR 条件组 | 生成受控表达式，几乎不会写错 |
| **高级模式** | 懂 SQL 的人 | 裸表达式编辑，语法高亮 + 失焦即调 `/metric/validate` | 需 L1–L4 全链兜底 |

简单模式覆盖现有配置的绝大多数场景。例如下面这条真实配置：

```yaml
where: "abx_used = 1 AND culture_first_time IS NOT NULL AND culture_first_time <= abx_first_time"
```

在简单模式里就是三个条件：

1. 字段 `abx_used` `=` `1`
2. 字段 `culture_first_time` `IS NOT NULL`
3. 字段 `culture_first_time` `<=` 字段 `abx_first_time`（需支持「与另一列比较」，与「与常量比较」并列）

只有 `EXISTS(子查询)` 这类复杂逻辑才必须切高级模式 —— 而这类逻辑**绝大多数在事实层、不在指标层**，因此指标层的简单模式足够用。

业务人员的典型操作路径（不需要任何 SQL 知识）：

```
选指标 → 看当前口径的中文描述 → 改数字/改字段/加条件 → 点「校验」
       → 看到「预计分子 X 人 / 分母 Y 人 / 值 Z%」→ 确认保存 → 生效
```

> 建议在简单模式顶部用一句话回显当前口径的自然语言描述（由 DSL 反向生成），
> 让业务方能「读懂自己配的是什么」，这是该功能能否被真正用起来的关键。
> 已实现的形式是**回显实际口径表达式本体**（`实际口径：(a = 1 AND b = 2) OR (c = 3)`）：
> 成本更低、且与最终落库内容逐字一致，不会出现「自然语言描述与实际口径不符」的二次风险。

### 6.3 OR 条件组与 SQL 优先级（已落地）

简单模式的行带**组号**：同组内是「并且」，不同组之间是「或者」，行上以下拉框切换组号，
配「+ 加一行」（跟随末行组号）/「+ 加一组（或）」。

```
单组：  a = 1 AND b = 2                     ← 不加多余括号，与历史口径逐字一致
多组：  (a = 1 AND b = 2) OR (c = 3)        ← 每组整体加括号
```

**往返比对是这里的护栏**：高级模式 → 简单模式时，先结构化再按同样规则拼回，
只有**逐字还原**才允许切换，否则保留高级模式并提示原因。绝不「猜一个差不多的口径」。

**配套修了一处 SQL 优先级缺陷**（`SqlCompiler#numCondition`）：原实现把 `where` 与分子附加条件
直接拼成 `where + " AND (" + numerator + ")"`。一旦 `where` 含顶层 `OR`，由于 AND 优先级高于 OR，
`(A) OR (B) AND (C)` 会被解析成 `A OR (B AND C)` —— **分子口径被悄悄放大，页面上完全看不出来**。
现改为把 `where` 片段整体加括号。对单个条件无副作用，因此统一加、不做「是否需要」的判断。

> 该缺陷在 OR 条件组上线前不会被触发（单组不产生顶层 OR），属于「新能力把老缺陷暴露出来」，
> 已在 `QualityConfigValidatorTest#orConditionGroupKeepsPrecedence` 中固化为回归用例。

| 风险 | 应对 | 落地情况 |
|---|---|---|
| 让业务人员在页面写 SQL = 开放生产库查询能力 | L1 安全校验 + L4 试跑 + 权限隔离 + 简单模式优先 | 已落地（写接口 fail-closed） |

| 历史结果口径无法回溯 | `expr_version` 自动递增 + `quality_def_history` 快照 | 已落地 |

| 计算中改配置 | reload 原子替换；正在跑的批次固定在开始时的快照上 | 已落地 |

| 一份来路不明的文件覆盖线上口径 | 导入默认 `skip`；覆盖需显式选择并二次确认 | 已落地 |

## 八、迁移步骤

P0–P4 已全部交付，因此这里给的是**一份完整的上线流程**，而不是分期步骤。

### 8.1 部署清单（按顺序）

1. **建表**（幂等，可重复执行）：
   ```bash
   # 在 zing_doctor_db_prod 下执行
   sql/10_quality_config.sql
   ```
   建出 `quality_metric_def` / `quality_fact_def` / `quality_def_history` 三张表。

2. （可选）把 `quality/` 配置目录复制到 jar 外部 —— 仅当需要「改 YAML 即生效」时才需要：
   ```bash
   mkdir -p /data/zing-doctor/config/quality
   cp -r /tmp/zing-doctor/config/quality/* /data/zing-doctor/config/quality/
   ```

3. **配置写接口保护（必须先做这一步再开放页面）**：
   ```yaml
   zing:
     quality:
       # ① 真源切到数据库：不切则配置页只能看、不能改
       config-source: db
       # ② 写接口 IP 白名单（推荐，逗号分隔，支持前缀匹配整段）
       config-write-ip-whitelist: 100.120.1.104,10.0.0.
       # ③ 或改用令牌（与 ② 至少配一个；两个都配则都必须通过）
       config-write-token: ${QUALITY_CONFIG_WRITE_TOKEN:}
       # ④ 仅当需要「改 YAML 也生效」时配置
       config-dir: /data/zing-doctor/config/quality
   ```
   > **不要跳过 ②/③**：两项都不配时 `POST /api/quality/config/**` 一律 403（fail-closed）。
   > 启动日志会打印写保护状态，可见 `[质控配置] 写保护已启用：...` 或一条明确的未配置 WARN。

4. **重启** → 配置表为空时自动从 `classpath:quality/*.yaml` **导入 127 条指标 + 10 个事实层种子**。
   日志应出现 `[质控] DSL 加载完成：数据源 2 个，事实层 10 个，指标 127 条`。

5. **验证**：打开 `quality-config` 页
   - 顶部横幅应显示「配置真源：数据库 ｜ 保存即生效 ｜ 操作人：xxx」；
   - 指标数应为 127，与看板一致；
   - 随便选一条指标点「校验」（只读，不写库），应返回试算值而非 `403`。

### 8.2 回退

| 想回退到 | 操作 |
|---|---|
| 配置页只读 | 移除 `config-write-ip-whitelist` 与 `config-write-token` 并重启（或临时设 `config-write-ip-whitelist: 127.0.0.1`） |
| 真源回 YAML | `config-source: yaml` 并重启。**DB 里的配置不会丢**，改回 `db` 即恢复 |
| 单条口径出错 | 配置页「变更历史」Tab → 找到上一版本 → 回滚（会以旧口径重新发布一次，审计链保留） |
