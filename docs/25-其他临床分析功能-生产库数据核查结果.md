## 0. 结论总览

| 模块 | 可行性分级 | 一句话结论 |
|---|---|---|
| 1 生命体征趋势 | **可直接做** | 7 项核心指标编码齐全、覆盖 1190 患者 / 20 万+条 |
| 2 体液平衡分析 | **降级做** | 四类来源通道齐全，但 `io_type='i'` 配置从未被使用；净平衡须逐窗验证去重 |
| 3 血流动力学分析 | **可直接做（承诺降级）** | MAP/乳酸/升压药双链路（开立+执行）齐备；心排量类不承诺 |
| 4 肝功能趋势 | **可直接做** | 7 个项目编码齐全、覆盖 4 万+患者；**ALT 存在第二编码，必须按名称匹配** |
| 5 凝血功能趋势 | **降级做** | 5 项覆盖良好；**D-二聚体仅 ICU 床边项目（280 患者/90天），须标注低覆盖** |

**通用发现（影响实现方式）**：
1. LIS 同一项目存在**新旧两套编码**（如 ALT 有 `100080` 与 `5271693919059922083` 两套，
   血小板相关项目多达 5 个）—— 一律按 `lis_item_name` 精确匹配 + code 取并集，
   不可只按 code 查，否则漏掉近半数据。
2. 项目名普遍带 `*` 前缀（异常标记），名称匹配要兼容。
3. 观察项血压分无创/有创两套编码，需并列展示并标明来源。

## 2. 体液平衡分析（降级做）

**四类来源通道（代码已实现）**：

| 来源 | 表 | 过滤 | 状态 |
|---|---|---|---|
| 出量（尿/引流等） | `patient_io_module_item_record` JOIN `config_io_item` | `c.io_type='o'`（647 个配置） | 已有 3 个方法 |
| 尿量 | 同上 | `item_code='ii_nl'` | 已有 4 个方法 |
| 医嘱入量 | `patient_advice_execute` | `is_to_io='1'` | 已有（含 07:00 交接班边界版） |
| 其他入量 | `patient_io_module_item_record` JOIN `patient_io_module_item` | `module_code='io_in'` | 已有 |

**核查发现的两个风险**：
1. `config_io_item.io_type` 有 **i(252) / o(647) / d(65)** 三类配置，但现有代码**只用 `io_type='o'`**；
   入量走 `module_code='io_in'` 通道。两条通道是否重复计量同一事件，**未能证明已去重**。
2. `ii_nl` 是否同时以名称项重复保存（方案 §4.2 的疑问）——需在联调时用同一患者同时段数据比对。

**结论（降级方案）**：一期**只按来源分栏展示**（出量 / 尿量 / 医嘱入量 / 其他入量各自聚合），
**不提供"净平衡"合计数**——方案 §3.2 要求"来源可解释且已去重后才计算净平衡"，
去重证据不足前不给总量。页面明确标注"各来源分列，未合并"。

## 3. 血流动力学分析（可直接做，承诺降级）

| 要素 | 数据源 | 编码/过滤 | 覆盖 |
|---|---|---|---|
| MAP / 血压 | observe 记录 | `oi_pjy`/`oi_ycpjy` + 收缩舒张编码 | 见 §1 |
| 乳酸 | `patient_info_lis_item` | `乳酸浓度` code `8000214`（3782 患者）；既有代码按 `lis_item_name LIKE '%乳酸%' AND NOT LIKE '%脱氢酶%'` 排除 LDH | 12,851 条 |
| 升压药（开立/执行中） | `patient_advice` | `status IN ('1','3')` / `status='1'` | 已有 4 个方法 |
| 升压药（实际执行+剂量/调速） | `patient_advice_execute` + `_drug` + `_step` | 时间重叠判定，剂量与调速步骤可还原 | SOFA 已在用 |

**不承诺**：心排量/每搏量/SVR/PVV/液体反应性（无结构化数据）；升压药剂量单位混杂时显示原始单位，不强行归一。
**结论**：可做"趋势 + 证据时间轴"；剂量换算待单位规范且临床确认后启用。

## 6. 数据质量与实现约束（来自本次核查）

1. **项目名带 `*` 前缀**（异常标记），名称匹配用包含而非相等，或先去 `*`。
2. **同一项目多编码**（ALT 两套、血小板 5 项、PCT 3 项）——按名称匹配 + code 白名单，不盲信单一 code。
3. **血压双来源**（无创 `oi_wc*` / 有创 `oi_yc*`）必须并列标注，不合并。
4. **参考范围**：结构化字段 `lis_item_low_value` / `lis_item_height_value` + 文本 `lis_item_limit`（Java `parseLimit()` 兜底）；缺参考范围不自行套通用范围。
5. **时间语义**：`check_time`（检验时间）与报告时间分列，不混用。
6. **软删与状态**：`del_flag=0` + `status=1`（既有查询均带，保持一致）。
7. 查询一律按 `in_hospital_no` + 有界时间窗驱动，不用 `SELECT *` 拉全量。

## 8. 补充核查（2026-10-13，编码修正）

按方案 §7「不一致处标记为阻塞项，不自行选看似合理的编码」要求，补充核查后发现两处与常识命名不符：

| 项目 | 文档/常识名 | 生产库实际 | code | 覆盖 |
|---|---|---|---|---|
| AST | 天冬氨酸氨基转移酶（**查无此名**） | **天冬氨酸氨基转氨酶** | `100090` | 56,477 条 / 45,166 患者 |
| AST/ALT 组合项 | — | **谷草/谷丙**（单字段含两个值，如"35/28"） | `100100` | 54,875 条 / 44,398 患者 |

**结论**：
1. AST 按 `天冬氨酸氨基转氨酶` 名称匹配（实现已按此修正），不按标准医学名词"转移酶"匹配——按后者查不到任何数据。
2. `谷草/谷丙` 组合项**不纳入**肝功能页面：单字段双值，拆分规则未经临床确认，
   强行拆分等于自行猜测数值。页面可在明细中标注"存在组合项未纳入"。
