# 其他临床分析功能：数据核查与实施方案

> 版本：v1.0（待 ICU 生产库只读核查后定稿）  
> 更新日期：2026-10-13  
> 状态：产品与技术方案初稿；数据覆盖率、项目编码、单位和业务口径尚须现场确认。  
> 适用项目：zing-doctor 重症医生决策与质控平台。  
> 配套文档：`docs/20-镇痛镇静与急性脑损伤监测分析模块-实施方案.md`、`docs/21-阶段0数据口径复核记录.md`、`docs/24-营养支持分析-数据盘点与实施方案.md`。

## 0. 结论先行

本方案把前面讨论的其他临床分析方向拆成**不同菜单、不同页面、各自有明确临床问题**的模块，不再把所有趋势图塞入诊疗摘要或一个“大数据分析”页面。页面可复用同一套日期筛选、趋势图、结果表和数据状态组件，但业务数据、解释、统计口径保持独立。

仓库代码及现有文档已经证明部分数据通路存在：患者监测记录、检验明细、血气、体温、出入量、尿量、医嘱执行和呼吸机参数均有相应查询代码。但这**不等于生产库覆盖完整或字段语义已确认**。新增临床解释、告警阈值、分母/率值、剂量或摄入量换算，均须先完成数据核查和临床会签。

建议纳入方案的独立页面：

1. **生命体征趋势分析**：患者级多指标时间窗回顾；提供指标勾选组合，不自动诊断。
2. **体液平衡分析**：分别呈现实测出入量、尿量、医嘱执行入量和累计平衡；先厘清来源与重复计量。
3. **血流动力学分析**：MAP/CVP/乳酸等可得指标趋势，以及升压药执行记录时间轴；高级心排量等未确认前不承诺。
4. **肝功能趋势分析**：基于 LIS 检验报告的肝功能指标纵向查看，不生成未经验证的肝衰竭判断。
5. **凝血功能趋势分析**：基于 LIS 的血小板及凝血项目趋势；项目编码、单位、参考范围待核实。
6. **肾功能分析**：不新建重复 AKI 识别；扩展现有 AKI 页面/模块，连贯展示肌酐、尿量、体重可用性、肾替代治疗线索。
7. **呼吸支持分析**：不新建重复 ARDS 页面；在现有 ARDS 监测页面扩展呼吸机参数与氧合历史分析。
8. **感染与抗菌药分析**：不另造感染决策页面；增强现有疑似感染、培养、抗菌药决策/复评模块之间的患者级时间关联。
9. **营养支持分析**：范围和数据库核查任务见方案 24，本文不重复设计。

其中 1–5 是候选新增独立菜单；6–8 明确按现有功能扩展，避免患者面对两套相同功能。最终是否拆分、命名及菜单顺序，应以数据核查结果和临床使用流程确认。

## 1. 与现有系统的边界

| 方向 | 当前项目已有基础 | 本方案采取的边界 |
|---|---|---|
| 患者和科室 | `patient_info`、科室范围服务、患者工作台 | 沿用患者 episode 与权限边界；不以客户端传入患者/科室参数替代后端鉴权 |
| 生命体征 | `patient_observe_module_item_record`、`config_observe_item`；有患者监测记录查询 | 只展示配置映射确认后的值、单位、时间和记录人；不把缺值解释为正常 |
| 体温 | Mapper 已有 `selectLatestTemperature`、`selectTemperatureTrend` | 可复用已有查询，但需核实时间窗、项目编码、测量部位和单位；不重复摘要页的小型 24h 图 |
| 出入量 | 有 `selectIoRecords`、`selectOutputByPatient`、`selectOtherIntakeByPatient`、`selectUrineByPatient`、`selectAdviceIntakeByPatient` 等查询路径 | 先核对来源、时间粒度、结算周期、退补录和重复关系；不把全部医嘱或所有入量简单相加 |
| 血流动力学 | 有观察记录查询、乳酸查询、升压药医嘱/执行查询；SOFA 已使用 MAP 与升压药相关数据 | 做趋势回顾和证据并列；不要把有升压药医嘱等同于实际持续给药，也不承诺高级血流动力学监测 |
| LIS | `patient_info_lis_item` 查询已被感染、AKI、SOFA、ARDS 等功能使用 | 复用经确认的检验映射；禁止无界扫描千万级 LIS 明细；不以异常标记代替临床诊断 |
| 肾功能 | 已有 AKI 识别逻辑/数据读取路径：肌酐、尿量等 | 复用现有 AKI 实现；本方案仅规划扩展趋势、数据完整性与治疗过程查看，不复制一套 AKI 分级 |
| 呼吸 | 已有 ARDS 监测、氧合历史、呼吸机参数趋势、俯卧位记录 | 继续完善现有 ARDS 页面；避免再加一个重复的“呼吸分析”总菜单 |
| 感染/抗菌药 | 已有疑似感染、培养/微生物、抗感染决策、复评、DDD/MDRO 等 | 增强跨模块联动与时间轴，不重做抗菌药规则或感染自动诊断 |
| 营养 | 已形成方案 24 | 依方案 24 单独核实医嘱、实际执行、配方成分、体重与目标；不得从医嘱名称推算能量/蛋白 |

## 2. 菜单与页面设计总则

### 2.1 独立页面，而非一个综合页

建议菜单项分别为：

- 生命体征趋势
- 体液平衡分析
- 血流动力学分析
- 肝功能趋势
- 凝血功能趋势
- 肾功能与 AKI（沿用现有页面/入口）
- ARDS/呼吸支持（沿用现有页面/入口）
- 感染与抗菌药（沿用现有页面/入口）
- 营养支持分析（方案 24）

菜单可以按临床工作流分组，但每个菜单进入独立路由和独立内容区。不要把所有模块塞进一个页面后用一排标签模拟多个功能。患者工作台选中患者后，由快捷入口带入现有患者上下文；直接从菜单打开时，使用现有患者选择流程。摘要页只保留入口，不重复堆功能卡片。

### 2.2 页面通用交互

- 患者上下文：姓名/床号等按现有系统策略展示，标明住院 episode、入科时间和科室，避免同一住院号多次入科串数据。
- 时间范围：默认近 24 小时或近 7 天，由对应业务决定；提供预设区间和自定义起止时间，禁止不设上限的历史查询。
- 趋势选择：仅在本模块已有且口径一致的项目间组合；不同量纲用独立 Y 轴或拆分图表，不能共用同一刻度造成误读。
- 明细联动：趋势点可查看原始报告/记录时间、项目名、结果、单位、参考范围、记录来源；展示检验时间和报告时间时不得混为一列。
- 数据状态：每个区块使用 `AVAILABLE`（有数据）、`NO_RECORD`（成功查询但无记录）、`PARTIAL`（部分指标有值/字段不全）、`UNKNOWN`（查询失败或数据源不可用）。`NO_RECORD` 不代表“正常”或“未发生”。
- 刷新信息：显示所选时间窗和数据更新时间；查询失败可单区块重试，不能静默回退成 0。
- 组合分析：一期只允许选择指标、同窗显示趋势和原始值；不提供任意公式编辑器，不允许用户自定义未经审核的风险阈值。

## 3. 候选独立模块设计

### 3.1 生命体征趋势分析

**定位**：让医生在指定时间窗内回顾基础生命体征及其同步变化。它是数据回顾工具，不是早期预警评分，也不替代 SOFA/APACHE II、床旁监护仪或临床判断。

**建议页面**

- 指标选择：体温、心率、呼吸频率、收缩压/舒张压/MAP、SpO₂；仅显示经 `config_observe_item` 和真实值分布核验可用的项目。
- 默认视图：近 24h 趋势 + 原始记录表；可扩至 72h/7d。支持选择 2–4 项叠加，异量纲指标自动拆图或使用清晰标注的双轴。
- 记录表：时间、项目、值、单位、来源/记录人；重复点保留原始记录，不用插值制造连续数据。
- 体温可由已有体温趋势逻辑接入，但需核实不同测量部位能否区分；没有部位字段时显示“记录值/部位未标明”。

**不做**：自动判定休克、脓毒症、发热病因；用单次异常创建待办；把监测频率不一致的值重采样后当作实测值。

**可行性**：基础观察项查询为**已有代码基础、具体项目覆盖待核查**。心率、呼吸频率、血压和 SpO₂ 的编码、名称、单位、异常/删除标志及频率须从配置表和生产记录复核。

### 3.2 体液平衡分析

**定位**：把一个明确时间窗内“记录到的入量、出量、净平衡和尿量”按来源并列呈现，便于人工核对液体变化。

**建议页面**

- 筛选周期：最近 6h/12h/24h、班次、自然日、自定义区间；默认不跨患者 episode。
- 入量明细分来源：I/O 手工/监测记录、医嘱执行明细、输血或其他已确认来源。每类先分别显示，不立即合并。
- 出量明细：尿量、引流/其他出量等按配置项目显示；尿量注明导尿管数据状态和记录间隔。
- 汇总：来源可解释且已去重后才计算“已记录入量、已记录出量、净平衡”；若来源不全，标注“部分记录汇总”并说明未纳入来源。
- 时间轴/柱状图：按小时或班次汇总，点击柱子下钻原始行；缺测时保留空白，不绘制为零。
- 体重信息仅用于附加展示；若需 mL/kg/h 或 mL/kg/day，须确认体重有效、单位、测量时间与分母适用窗口。无可靠体重时显示原始总量，不做 kg 校正。

**关键数据核查**：`patient_io_module_item_record`、`config_io_item`、相关 I/O 明细/配置表、`patient_advice_execute` 与执行小时明细；核实 `io_type`、`item_code`、`item_value`/`amount`、单位、记录时间、汇总周期、软删除状态、执行状态和补录/冲销语义。尿量编码 `ii_nl` 只作为现有项目线索，须确认同一时间是否还以名称项重复保存。

**不做**：把计划医嘱等同于实际输入；把“医嘱计入 I/O”和 I/O 手工记录重复相加；把液体平衡结果直接写成容量状态/液体反应性结论；按缺项推断无尿。

**可行性**：出入量查询已有代码基础；各来源能否可靠去重、能否形成完整净平衡，属于**必须先核实**。

### 3.3 血流动力学分析

**定位**：按同一时间轴查看可得的血压/MAP、CVP、乳酸及升压药执行证据，帮助医生回顾循环支持过程。

**建议页面**

- 趋势区：MAP/血压、乳酸；CVP 仅在真实数据存在且单位确认时加入。按指标分图，支持共用时间轴。
- 用药时间轴：显示升压药名称、执行时间、已确认的剂量/单位/泵速变化；处方、执行单、调速步骤分别标明来源。
- 事件线：检验采样时间、升压药执行/调速时间、血压记录时间并列，辅助回顾时间关系；不自动推导治疗效果或因果。
- 汇总区：所选窗口最低/最高/最近 MAP、乳酸值和时间；仅在采样点和单位完整时显示，不用插值计算持续低血压时长。
- 后续可扩展液体入量联动，但须复用体液平衡模块的去重后数据，不自行再求一份不同口径的总液体量。

**数据源线索**：`patient_observe_module_item_record` / `config_observe_item` 的 MAP、血压、CVP 等项目；`patient_info_lis_item` 的乳酸结果；`patient_advice_execute`、`patient_advice_execute_drug`、`patient_advice_execute_step` 的升压药执行与调速。项目已有 `selectLactateResults`、`selectVasopressorAdvice`、`selectCurrentVasopressorAdvice` 等查询路径；复用前须复核实际筛选状态和时间字段。

**不承诺**：心排量、每搏量、SVR/PVR、超声 EF、液体反应性、血管活性药剂量等价换算、休克分型。上述数据结构/单位未确认前不出现在菜单承诺和指标清单中。升压药剂量单位混杂时显示原始单位与来源，不强行归一。

**可行性**：基础生命体征、乳酸、升压药存在代码路径；跨源的完整性和时间同步属**部分可行，需专项核查**。

### 3.4 肝功能趋势分析

**定位**：独立检验趋势页，展示肝功能相关检验的历史结果及报告参考范围，不由趋势直接诊断急性/慢性肝衰竭。

**拟纳入指标**：ALT、AST、总胆红素、直接胆红素、白蛋白、ALP、GGT 等；仅纳入生产库检验项目名称/编码/单位可稳定确认者。总胆红素与直接胆红素必须区分，不可用同类候选编码替代。

**建议页面**：按“肝细胞损伤 / 胆红素 / 合成功能”分组（分类只用于浏览，不是病理诊断）；显示时间序列、原始检验值、单位、参考范围、检验/报告时间和来源。不同单位并存时分轨显示或明确转换依据；不把参考范围异常标记当严重程度分级。

**数据核查**：`patient_info_lis_item` 的 `lis_item_name`、`lis_item_code`、结果、单位、参考值、异常标志、采样/检查时间、报告 ID、删除标志；按患者住院 episode + 时间过滤，核验同一报告重复行和结果文本格式。SOFA 文档记录的总胆红素候选 code 存在需区分总/直/间接的风险，本页不得直接复制未经确认的 code 列表。

**可行性**：LIS 源及通用检验查询已有，具体项目映射/覆盖率**待核查**。

### 3.5 凝血功能趋势分析

**定位**：独立查看血小板和凝血实验室项目的变化，不自动输出 DIC、出血风险或抗凝处置结论。

**拟纳入指标**：血小板、PT/INR、APTT、纤维蛋白原、D-二聚体等，以生产库实际存在和临床科室确认结果为准。

**建议页面**：检验项目分组趋势 + 明细表；保留报告参考范围、单位、标本/时间信息；支持对照时间范围内多个指标，但不同量纲分别绘制。对重复采样如实显示。

**数据核查**：复核 LIS 编码和名称，单位和参考范围是否随检验仪器/时间变化，结果文本是否包含 `<`、`>` 等比较符，是否有同一报告重复项目。血小板 code 在既有 SOFA 文档不同段落出现的候选值不完全一致，须以生产配置和实际结果校对，不能按文档猜测。

**可行性**：LIS 支持情况为**待核实具体字段/覆盖率**；通过核查后可先做趋势回顾，临床评分/阈值另行审批。

### 3.6 肾功能与 AKI（复用现有模块，不重建）

现有项目已有 AKI/KDIGO 识别、肌酐历史、尿量查询路径。新增工作应限于：

- 将肌酐时间序列、尿量窗口与 AKI 结果来源/依据联动展示；
- 展示数据完整性、单位与体重适用状态；
- 如确有结构化记录，再加入肾替代治疗/CRRT 时间线；无可靠疗程边界时不计算治疗日数。

肌酐候选项、尿量 `ii_nl` 和体重字段均需维持现有 AKI 口径；不在新页面再算一套不同的 KDIGO 阶段，不因未取到体重就套成人固定尿量诊断阈值。CRRT 可依据现有记录入口核实，但“有当前 CRRT 标记”不能自动还原历史治疗时长。

### 3.7 呼吸支持分析（扩展 ARDS，不重建）

项目已有 ARDS 监测页，覆盖氧合指数历史和呼吸机参数趋势（包括潮气量、PEEP、FiO₂、呼吸频率、分钟通气量等已有映射）。后续优化应继续落在 ARDS/呼吸支持专项页：

- 明确参数实际采集时间、设置值/实测值语义、单位和缺测状态；
- 复核潮气量/kg 分母及身高/体重的可靠性；
- 对氧合指数、PEEP 和影像学等证据分别展示，不将简化筛查等级称作确诊；
- 仅在设备/治疗记录足够可靠后展示通气持续时间、俯卧位前后趋势。

不新增重复“呼吸分析”菜单，不把呼吸机设置值解释为患者实际测量值。

### 3.8 感染与抗菌药分析（增强现有模块，不重复建设）

项目已有疑似感染/脓毒症、培养和抗菌药决策/复评相关模块。建议新增的是跨模块的**时间关联与数据解释**，而非另建一个全新感染页面：

- 复用已有患者级诊断、体温/检验、培养报告、抗菌药实际执行、复评结果；
- 同屏或时间轴并列送培养、采样、出结果、首剂执行、后续复评时间；
- 细菌培养/药敏文本字段仍以原报告展示为主；结构化提取需验证，不能把文本解析结果作为正式药敏判定；
- 未送检、待报告、阴性、阳性、无结果和查询失败必须区分；
- 继续复用现有抗菌药词库、DDD/MDRO 等页面，不能复制一套药品分类规则。

感染诊断、脓毒症/感染性休克判定、院感事件归因仍由临床/院感流程完成；趋势页面不自动确诊、不自动纳入质控分子。

## 4. 生产库数据核查计划（交给可连库人员/AI）

本节用于先做事实核验，再决定开发范围。只允许**生产库只读查询**；不得执行 DDL/DML、索引修改或无界全表扫描。查询结果优先返回聚合计数、字段分布和少量脱敏结构样例；不导出姓名、完整住院号、诊断自由文本或其他可识别健康信息。

### 4.1 通用核查要求

1. 先记录数据库产品/版本、schema、核查时间、时区、统计窗口；确认实际连接库和项目 ICU 数据源一致。
2. 先核实列、类型、注释、索引、软删除和有效状态字段，再写 SQL；达梦与 MariaDB 方言分开处理。
3. 每类记录按**患者 episode + 有界时间窗**查询。`patient_info_lis_item`、observe 等大表优先从小的患者/住院范围驱动，并检查达梦执行计划与耗时。
4. 不仅报行数，还需报：记录数、去重患者数、去重 episode 数、最近记录时间、空值率、单位分布、异常结果字符串比例、项目映射覆盖漏斗。
5. 对结果样例只使用内部临时脱敏编号；不得把真实姓名、完整住院号、病历文本或敏感生产输出写入文档。
6. “表存在”“有历史行”不等于当前业务启用；按最近 30/90 天、近 12 个月分别验证。

### 4.2 分模块核查清单

| 模块 | 核查对象 | 必须回答的问题 |
|---|---|---|
| 生命体征 | `patient_observe_module_item_record`、`config_observe_item` | 体温/HR/RR/BP/MAP/SpO₂/CVP 对应编码、配置名、单位、数值比例、记录频次；项目是否有多个编码/测量部位；数据时间和记录时间是否相同；空值和软删除如何表达 |
| 体液平衡 | `patient_io_module_item_record`、`config_io_item`、患者出入量明细/配置、`patient_advice_execute` 与小时明细 | 各入出量编码、`io_type`、项目名称和单位；日/班次汇总规则；医嘱入量是否已同步到 I/O；退执行、补录、冲销如何识别；尿量编码是否重复；净平衡能否在每个时间窗可靠计算 |
| 血流动力学 | observe/config、LIS 乳酸、升压药执行主表/药品/调速步骤 | MAP/CVP/血压和乳酸覆盖；升压药药品字典与执行状态语义；剂量/速度单位分布及能否还原时间段；有无实际执行而非仅开立记录；是否存在 CO/CI/SVV 等结构化数据 |
| 肝功能 | LIS 项目、报告头/项目明细、检验项目字典 | ALT/AST/总/直接胆红素/ALB/ALP/GGT 的码名匹配率、参考范围/单位缺失率、跨单位变化、时间字段、同报告重复和结果文本格式 |
| 凝血 | 同上 | PLT/PT/INR/APTT/FIB/D-dimer 等真实项目列表和覆盖率；编码冲突；单位和参考范围变化；异常文本；标本和报告关联 |
| 肾/AKI | 现有 AKI 查询使用的肌酐、尿量、体重、CRRT 相关源 | 对照当前实现复核 AKI 输入字段、单位与记录时窗；体重有效数值比例和测量时间；CRRT/肾替代治疗时间序列是否可得。不得另造新的诊断口径 |
| 呼吸/ARDS | 现有 ARDS 参数、血气氧合指数、身高/体重及俯卧位记录 | 当前页面查询值与源记录一致性；实际/设置值语义；身高和体重可用率；机械通气起止和俯卧位起止能否还原；不重复统计已有数据 |
| 感染/抗菌药 | 现有培养报告、诊断、抗菌药执行和复评数据源 | 各事件时间字段、患者关联键、结果状态、培养文本结构、抗菌药执行/停用口径、模块间重复来源；不将文书文本自动转成确诊状态 |

### 4.3 数据报告建议格式

建议输出 `docs/25-其他临床分析功能-生产库数据核查结果.md`，逐项包含：

- 核查环境与口径（不含账号、密码、地址凭据）；
- 表/列/索引与代码查询方法的对应关系；
- 近 30/90 天及近 12 月覆盖率漏斗；
- 项目编码、名称、单位、数值格式、时间字段、有效/删除状态；
- 数据质量问题（重复、空值、非数值、单位混用、时间倒置等）；
- 每个页面的“可以做 / 降级做 / 暂不可做”结论；
- 脱敏案例只用模拟编号；
- SQL 及执行耗时/计划摘要，不存储敏感原始数据。

## 5. 实施顺序与阶段门

### 阶段 0：只读数据核查与临床定口径（开发前置）

完成 §4 数据核查；由 ICU 医生确认展示项目、时间窗口、计量单位及页面措辞。输出按模块的数据可行性分级。没有核查结果，不承诺具体覆盖率、趋势结论、临床阈值或统计率。

### 阶段 1：高可行性、事实回顾页面

优先开发：

1. 生命体征趋势（仅纳入已映射项目）；
2. 体液平衡分析（先按来源分栏，可靠去重后才计算合计）；
3. 肝功能和凝血检验趋势（按实际确认的项目逐批开放）。

这些模块以原始数据回顾为主，不加新诊断、不生成治疗建议。每个菜单、页面独立实现。

### 阶段 2：循环支持整合与现有模块增强

- 血流动力学：对齐血压/MAP、乳酸、升压药执行时间线；剂量换算仅在单位规范且临床确认后启用。
- 肾功能：完善现有 AKI 页面数据依据和趋势联动，不重复 AKI 分期。
- 呼吸：完善 ARDS 现有页面的数据来源/时间口径，不复制新页面。
- 感染：将培养、抗菌药执行和复评时间关系做现有页面联动，不新增另一套决策规则。

### 阶段 3：临床解释型分析（单独立项/审批）

只有在数据完整性、规则出处、临床签字、质控口径明确后，再考虑持续时间判定、目标达标率、风险预警、科室统计。阈值须有指南/政策来源和版本，不得仅凭页面开发方便设置。

### 每阶段验收门

- 数据口径和项目映射有临床/信息科确认记录；
- 典型患者、无记录、部分记录、重复记录、异常单位和查询失败用例通过；
- 数据展示与 ICU 源记录可追溯，缺失不显示为正常/零；
- 通过科室权限和患者 episode 校验；外链场景遵守现有入口权限/参数机制；
- 查询限制在患者与时间范围内，批量页面不得按患者逐次 N+1 调用；
- LIS/observe 大表经真实执行计划与性能验证，失败时区块级报错；
- 无任何对 ICU 源库的写入；日志不记录完整患者身份和检验明细。

## 6. 通用后端与前端技术约束

### 6.1 数据模型与接口建议

- 所有患者级接口使用 `patientId` 与住院 episode 校验，禁止只靠姓名或可复用的住院号判断身份。
- 入参含 `startTime`、`endTime`，由后端校验最大跨度和先后关系；患者来源和 `departCode` 必须经过服务端授权校验。
- 返回统一包含 `dataStatus`、`rangeStart`、`rangeEnd`、`sourceUpdatedAt`、`items`；单条记录包含项目编码/名称、原始值、归一值（如有）、单位、采样时间、报告/执行时间、来源和质量标记。
- 转换后的值保留原值与转换公式/版本，不能覆盖源数据。参考范围按源数据获取；缺少参考范围时不自行套实验室通用范围。
- 一个页面需要多个数据源时可并行独立加载，任一块失败不应伪装成空值；避免单个慢源阻塞整页其他区块。

### 6.2 权限、历史患者与外链

- 登录模式使用现有科室授权解析服务校验患者归属；外链模式遵循项目已有 `ExternalLinkContext`、页面注册与来源科室边界。
- 每个 API 都要验证，不能只在菜单隐藏或前端路由检查权限。
- 历史患者分析必须按真实住院 episode 时间截断；同一患者重复入科不可将不同 episode 的观察、医嘱、检验混为一条曲线。
- 禁止用前端传入的姓名、住院号或科室代码单独作为授权凭证。

### 6.3 性能与安全

- 患者主表/episode 做查询驱动；大表按患者键、检验/记录时间、删除标志以及必要项目编码限制查询。
- 不执行全院每患者多次查询；科室汇总需单独设计批量 SQL/预聚合，不复用患者详情接口循环调用。
- 约束时间跨度、分页和返回记录上限；对高频趋势可按真实数据量评估服务端降采样，但原始明细仍可追溯。
- 不从生产库复制个人健康明细到普通文档、截图或调试文件；接口/应用日志屏蔽敏感参数。
- 所有模块保持 ICU 数据源只读，不新增未经审批的索引或数据库对象。

## 7. 临床安全与数据解释原则

1. **原始事实与推断分层**：页面优先陈述“某时点记录值/某报告结果”，推断必须单列且披露依据。
2. **时间语义明确**：采样、报告、执行、录入、同步时间可能不同，按业务分别标注；不得把同步时间当临床事件时间。
3. **单位不可猜**：单位缺失、单位转换不明确或同项目多单位并存时保留原值并提示，不参与合计/比较。
4. **缺失不是阴性**：无培养结果不等于培养阴性；无尿量记录不等于无尿；未见支持数据不等于患者未接受支持。
5. **不做无依据阈值**：涉及发热、低血压、乳酸升高、实验室异常或持续时间阈值时，先确认本院/指南口径与适用人群并记录版本。
6. **不把趋势等同因果**：时间同时发生只能用于回顾，不能据此断言药物或干预导致结果变化。
7. **医生保留最终判断**：不自动确诊、自动停药/调药、生成处方或替代病历记录。

## 8. 可直接交给其他 AI/工程人员的核查任务

请在当前项目仓库中，仅依据已存在的代码和经授权的 ICU 数据库只读查询，完成“其他临床分析功能”的数据可行性核查。核查目标为生命体征趋势、体液平衡、血流动力学、肝功能、凝血；并确认肾/AKI、呼吸/ARDS、感染/抗菌药现有模块能否扩展复用。营养模块请遵循 `docs/24-营养支持分析-数据盘点与实施方案.md`，不要重复发明口径。

要求：

1. 先检索本项目 Mapper/Service/Controller，给出每个候选数据源的真实代码位置和当前过滤条件；不要只依据文档推断代码已实现。
2. 数据库只读；先查数据字典、列/索引/注释，再用带患者/住院 episode 与时间窗的聚合查询验证。严禁写库、建索引、无界全表扫描、`SELECT *` 拉取大量生产数据。
3. 对每个模块统计近 30/90 天和近 12 个月的记录数、脱敏患者数、住院 episode 数、最近记录时间、空值率、单位/项目分布、有效记录比例。明确分母、时间字段、去重键、软删除状态和 SQL 执行耗时。
4. 项目编码/名称映射要给实际聚合证据；检验结果中的 `<`、`>`、文本值与单位差异要报告。不要把候选编码或名称 LIKE 规则当成权威分类。
5. 单独验证出入量来源之间是否重复、执行记录是否确为实际执行、退/补/冲销语义；无法证明去重前，不给“净平衡”总量结论。
6. 对血管活性药，分别统计处方、执行主表、药品明细、调速记录覆盖率和单位分布；不能把开立处方计作实际用药。
7. 对项目代码与方案文档不一致处（含 SOFA 中血小板/胆红素等候选映射）标记为阻塞项，列证据，不自行选择一个看似合理的编码。
8. 不输出姓名、完整住院号、诊断自由文本、患者截图或原始病历片段。案例只用随机脱敏编号和聚合后的结构化摘要。
9. 交付 `docs/25-其他临床分析功能-生产库数据核查结果.md`，按每个模块给出“可直接做 / 降级做 / 暂不可做”、实际字段与映射、数据质量风险、建议一期页面范围及临床待会签事项。无数据时明确区分“未记录”“未启用”“查询失败”“无法确定”。

完成核查后，先更新本方案的数据状态表和实施优先级，再开始写业务代码；不以旧统计量作为当前生产库结果。
