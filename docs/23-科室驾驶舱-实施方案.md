# 科室驾驶舱实现方案

> 版本：实施设计 v1.0  
> 目标：为 ICU 科室负责人和医疗管理人员提供单页科室运营与质量总览。  
> 约束：先复用现有患者工作台、质控中台、出科统计和集束化模块；未核实的数据源显示“待接数据/暂不可用”，不虚构实时数值。

---

## 1. 建设目标与范围

### 1.1 目标

建设独立的“科室驾驶舱”页面，帮助管理者快速了解：

- 当前科室在科患者、危重/器官支持患者、当日入科与出科情况；
- 床位开放、占用与使用率（仅在床位口径和床位数据核实后展示）；
- 已具备数据源的质控指标及其趋势；
- APACHE II、SOFA 评分分布；
- 脓毒症集束化执行情况；
- 近 30 天患者流转情况；
- 医疗设备和人力资源数据接入状态。

### 1.2 产品形态

- 新建独立页面 `/page/department-cockpit`，不把科室管理图表塞入患者诊疗摘要页或质控指标看板。
- 左侧菜单增加“科室驾驶舱”入口；菜单分组建议放在“质控中台”之前，突出管理总览定位。
- 页面以**科室为主要筛选维度**，不要求先选患者；权限由当前登录账号的科室授权范围约束。
- 提供“今日 / 本月 / 近 30 天 / 近 12 个月”视图。实时区显示“数据更新时间”，首版采用页面刷新与短时缓存，不依赖 WebSocket。
- 页面可下钻到现有出科统计、质控看板、SOFA/APACHE II 总览、脓毒症集束化页面；涉及患者级明细时仍需后端权限校验。

### 1.3 本期不做

- 不新建设备维修、盘点、人员排班等业务台账；源系统没有数据前不编造“正常运行/在岗人数”。
- 不基于现有设备使用标记推导设备库存或维护状态。
- 不新建另一套质控口径引擎，不绕过现有质控中台重复计算相同指标。
- 不把预测病死率称作实际病死率；不对未确认的指标设置达标结论。

## 2. 页面信息架构

### A. 顶部筛选与数据状态

- 科室筛选：默认当前授权科室；有多个授权科室时可切换；全院管理员可选全院。
- 时间范围：今日、本月、近 30 天、近 12 个月；年度/月度趋势显示完整区间。
- 操作：刷新、最后更新时间、数据源/指标口径说明入口。
- 每个图表区块独立显示“已更新 / 暂无数据 / 待接数据源 / 查询失败”，避免整页被单一数据源故障拖成空白。

### B. 今日科室快照（首屏）

指标卡片建议：

1. 当前在科患者数；
2. 危重患者数及比例（沿用项目已有危重判定口径，展示口径说明）；
3. 今日入科/转入数；
4. 今日转出/出科数；
5. 床位使用率（仅在开放床位与占用床位定义、数据可靠后启用）；
6. 当前机械通气、CRRT、ECMO 患者数（只表达患者支持状态，不代表设备台数或可用库存）。

“医疗资源调配”首版只展示已知患者支持状态和床位信息，不自动提出排床或人力调度建议。

### C. 质量指标趋势

管理者选择指标后展示本月累计值及近 12 个月趋势。优先复用质控中台的已配置指标、统计结果和目标/预警配置。

建议优先呈现：

- ICU 实际病死率（若当前质量数据源和分子/分母状态可用）；
- 非计划气管插管拔管数/率（当前质控定义显示待接管路数据源，不能先显示为 0）；
- 计划拔管后 48 小时内再插管数/率（须明确分子分母及数据质量）；
- ICU 转出后 48 小时内重返指标（质控已有 `quality_22`，需核实统计窗口与当前需求是否一致）；
- ICU-09/10/18 等已核实的适用质量指标；
- 脓毒症集束化完成情况（参见下一节）。

病死率、非计划拔管、重返率等每一项均要显示分子、分母、周期、数据状态和口径版本；没有可靠分母或数据源时显示“待确认/暂不可算”。

### D. 患者流转（近 30 天）

- 入科/转入人数和转出/出科人数按日或周展示；
- 平均 ICU 住院日；
- 可选展示出科转归构成（转科、出院、死亡等）；
- 与现有出科统计使用同一出科时间口径、episode 去重和科室边界；
- 图表支持点击某日/月份进入现有出科统计并带入时间范围。

“入科率/出科率”必须先明确业务定义与分母；若仅表达数量变化，页面直接称“入科人数/出科人数”，不要套用含义不清的“率”。

### E. 评分分布

- APACHE II 分值区间分布、SOFA 分值区间分布，可切换今日/本月/近 30 天。
- 默认用**每个住院 episode 在所选周期内最新一条有效评分**参与分布，防止高频复评患者被重复计数；图例显示纳入人数、未评分人数、时间范围。
- APACHE II 预测死亡率单独标为“预测值”，不得与实际病死率合并。
- 如果对“全体在科患者最新评分”或“周期内评分记录分布”有管理需求，应提供明确切换选项并说明统计单位，不能混用“患者数”和“评分次数”。
- 点击区间可按授权下钻至对应患者/评分总览；按最小必要原则控制敏感信息。

### F. 脓毒症集束化（近 12 个月）

- 按月展示 1h、3h、6h 完成率/完成情况，并可查看病例数及可计算病例数。
- 复用现有脓毒症集束化模块规则与质控中台数据；如果现有记录覆盖率不足或只有系统内手工记录，须标明“本系统记录覆盖范围”，不能表述为全科实际完成率。
- 只有在病例识别口径、分子/分母、无记录与未完成规则明确后，才展示“完成率”；缺失记录不能自动视为未完成，也不能自动视为完成。

### G. 设备与人员资源（数据接入后开放）

页面预留设备/人员区块，但初始可显示数据接入说明：

- 设备：需要 ICU/HIS/设备管理系统提供设备台账、设备类型、科室归属、当前状态、维修状态、状态更新时间。呼吸机/监护仪患者使用情况不等于设备总量、空闲量或维护状态。
- 人员：需要组织架构/排班数据提供科室、岗位、有效在岗状态、班次与统计时点。质控中台当前医师/护士总数为人工填报或待接数据，不等于实时在岗人数。
- 医师床位比、护士床位比应注明统计口径（开放床位还是占用床位、人员总数还是当班人数、统计时点），数据未齐不得显示实时比例。

## 3. 指标口径与数据可得性盘点

| 需求 | 项目内已有基础 | 实施处理 | 开发前必须确认 |
|---|---|---|---|
| 当前患者数/危重患者比例 | 患者工作台有在科列表、危重/生命支持标记 | 复用同一患者范围和危重判定；汇总接口按科室批量统计 | 危重定义、转科/重复 episode 去重、统计时点 |
| 今日入科/出科、近30天流转 | 出科统计及 `fact_patient_stay`、`quality_0/2/16/22/23/403` 等现有定义 | 能复用则复用；统一左闭右开时间区间，使用单独聚合查询 | 入/转入、转出/出院边界；平均住院日算法；跨月 episode 规则 |
| 床位使用率 | 质控事实层 `fact_bed` / 指标 `quality_301/304`；ICU 侧另有「ICU床位使用率」规则（`quality_2 ÷ quality_301 × 100`） | **已实现两种口径，页面上分别标注**：①当前实时快照 = `config_bed` 中有效开放床位 ∩ `patient_info` 当前在科患者床号；②本月质控口径 = 直接复用上述质控规则的结果（不重算）。两者数值不同属正常。注意 `config_bed` **没有 `status` 列**，过滤只能按 `del_flag` + 启停区间，与 `fact_bed` 的 where 条件一致 | 实际开放床位、暂停床位、临时床位、占用床位和统计时点 |
| ICU 病死率 | 质控有 `quality_16`、`quality_30` 等相关定义 | 优先复用真指标结果；如结果不可算，显示状态而非临时另写公式 | 指标实际分母、患者/episode 去重、出科转归、周期边界 |
| 非计划拔管/再插管 | `quality_17/18/19` 在现有定义中待接管路数据源 | 数据源接通并临床确认后展示；此前列为待接 | tube 事件、计划属性、时间配对、拔管后窗口、分母 |
| 48h ICU 重返 | `quality_22` 已存在 | 先对齐用户所说“转出后重返率”的定义和现有质量指标 | 分子/分母、出科与再次入科关联、episode 间隔算法、按患者还是次数 |
| APACHE II/SOFA 分布 | APACHE II、SOFA 模块及记录表已存在 | 一次批量查询各科室周期内最新有效评分，再聚合区间 | 记录有效状态、episode 归属、评分时间、区间分档 |
| Sepsis bundle 近一年 | 集束化功能已有判定/记录；质控有 `fact_sepsis_bundle` | 优先复用质控中台按月结果；不足时只显示覆盖范围 | 感染性休克病例分母、手工记录/自动判断的纳入规则、重复评估去重 |
| 医师/护士床位比 | 当前人力指标存在 MANUAL/待接状态 | 暂不宣称自动或实时；接口和人员数据到位后开放 | 医护人数定义、当班/在岗、床位口径与数据时点 |
| 设备状态/维护 | 当前项目已能识别部分患者生命支持状态；未见已验证的完整设备资产维护源 | 不在一期计算设备可用率；先留区块和接入清单 | 设备资产/维护 API 或表、状态字典、维护责任方 |

> 质控中台里原子指标与业务率指标是两层：驾驶舱展示率时优先用现有 `quality_count_rule` 组装出的真指标，不把 `quality_xxx` 原子计数误当成率。

## 4. 数据接口与系统设计

### 4.1 API 建议

新增只读科室驾驶舱聚合接口，例如：

- `GET /api/department-cockpit/summary?departCode=&periodType=&periodStart=`：顶部快照、时间范围、更新时间和各区块数据状态；
- `GET /api/department-cockpit/flow?...`：近 30 天/自定义区间患者流转趋势；
- `GET /api/department-cockpit/scores?...`：SOFA/APACHE II 分布；
- `GET /api/department-cockpit/quality?...`：返回复用的质控指标及其月份序列；
- `GET /api/department-cockpit/bundle?...`：集束化月度情况。

实际接口数量应按现有后端服务结构决定。首选一个**轻量汇总接口 + 按需区块接口**，避免首页同时触发多个长查询；不要把多个患者详情接口循环调用来拼驾驶舱。

### 4.2 复用原则

1. 质控趋势复用 `QualityCountRuleService` / `QualityQueryService` 或月度结果；不在驾驶舱重算相同的病死率、重返率、集束化率。
2. 患者流转优先复用现有出科统计口径与患者事实层；若现有接口返回明细而非汇总，新增批量聚合 SQL，不应把全部患者记录传到浏览器再统计。
3. APACHE II/SOFA 可以复用现有评分查询与患者 episode 关系；驾驶舱按周期一次性批量聚合。
4. 只有确认来源、口径和权限后才将数据纳入卡片；当前没有数据不以静态 0 填充。

### 4.3 性能、缓存与安全

- 所有查询必须受 `departCode` 授权范围限制，并在服务端验证，不能信任前端传入的科室编码。
- 明细查询和时间范围查询必须限制时间窗、批量执行、避免 N+1；不得以全院扫大表实现实时驾驶舱。
- 区分“快照时间”和“临床事件时间”；页面标注最近刷新时间。实时区块可以 1–5 分钟短缓存，历史月度质控依赖已完成计算批次。
- 目标时延：首屏摘要 P95 ≤ 2 秒；图表区块 P95 ≤ 3 秒（以联调环境测量，超出则降级为懒加载/缓存，不阻塞首屏）。
- 区块级错误隔离：某一质控指标或设备源失败，不影响患者快照和其他图表。
- 患者级下钻按现有权限和审计策略执行；科室汇总默认不直接展示患者姓名等非必要信息。

## 5. 分期实施

### 阶段 0：数据与口径核验（前置）

交付：需求—指标—源表/接口—过滤条件—分子/分母—刷新频率—数据状态矩阵；由 ICU 管理者/质控人员确认关键指标定义。

重点核查：床位数据源、病死率/重返率分母、非计划拔管源、SOFA/APACHE 分布按患者还是记录、集束化分母、设备和排班数据是否存在。

### 阶段 1：科室运营快照与流转（MVP）

实现：今日在科、危重与生命支持人数、今日入出科、近 30 天入出科趋势、平均 ICU 住院日（口径确认后）。床位使用率若未通过数据核验则显示“待接床位数据”。

### 阶段 2：质控与评分分析

实现：可用质控指标趋势、APACHE II/SOFA 分布、近 12 个月集束化月趋势。复用现有质控结果，不重写规则；暂不可算项保留状态与原因。

### 阶段 3：设备与人力资源

待 ICU/设备/人事排班数据接口确认后实施。包括设备台账状态、维护状态、当班人员口径、医护床位比。需科室/信息/设备管理方验收。

### 阶段 4：优化与告警（可选）

在口径稳定、数据刷新可靠后，再评估异常趋势提示、阈值和改进跟踪。首版不生成自动排班/排床决策，不自动做绩效排名。

## 6. 验收标准

### 页面与交互

- [ ] 存在独立菜单和路由；刷新、切换科室、时间范围均正常。
- [ ] 当前用户只能查看授权科室；伪造未授权 `departCode` 被后端拒绝。
- [ ] 首屏清楚区分今日快照、历史趋势和质量指标；每块显示统计周期/更新时间。
- [ ] 图表支持 tooltip、空态、区间下钻；窄屏布局可用。
- [ ] 设备、人力、床位数据未接入时明确显示待接入，不显示虚假 0 或“正常”。

### 口径与数据

- [ ] 同一科室同一周期与质控中台/出科统计按相同公式和人群对得上。
- [ ] 病死率与 APACHE II 预测病死率明确区分。
- [ ] ICU 重返率、非计划拔管指标分子分母与院方确认；不可算时呈现缺口状态。
- [ ] APACHE II/SOFA 分布按选定的患者/episode/记录统计单位去重，图例显示样本数和未评分数。
- [ ] Bundle 覆盖范围与完成判定可追溯，缺失数据不默认为完成或未完成。

### 性能与回归

- [ ] 无逐患者 N+1；大表查询有科室/时间条件和执行计划验证。
- [ ] 首屏及区块耗时达到项目设定目标；超时只影响对应区块。
- [ ] 达梦/MariaDB 双适配通过；构建、单测、接口测试通过。
- [ ] 现有质控看板、出科统计、患者工作台不回归。

## 7. 需要院方确认的决策项

1. 床位使用率分母采用实际开放床位、核定床位还是可运行床位？封床/临时床如何处理？
2. “危重患者”按当前系统哪个字段/临床口径识别？比例分母按当前在科患者还是开放床位？
3. 平均 ICU 住院日按已出科患者、所有住院 episode，还是当前在科患者截至今天？
4. 病死率、48 小时重返率和非计划拔管率的院内目标及分子/分母口径是什么？
5. Sepsis bundle 完成率的病例纳入、重复评估、无记录与补录规则是什么？
6. 设备资产与维护数据由哪个系统提供？是否可提供实时状态 API？
7. 医师/护士床位比按科室人员总数还是每班实际在岗人数？统计时间点是什么？
8. 驾驶舱下钻是否需要显示患者清单，哪些角色可以查看/导出？

## 给实现者的要求

先完成阶段 0，不要把方案表格里的“需求描述”直接当成已存在的数据源。开发前检查现有质控 YAML、事实层、出科统计接口、患者权限与菜单注册规范；把“可复用、需核实、缺数据源”列清楚，再按阶段交付。任何数据源或口径与本文不符，先提交差异和证据，不要自行猜字段或把 UNKNOWN 变成 0。
