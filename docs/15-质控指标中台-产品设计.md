# 质控指标中台 · 产品设计方案

> 版本：设计稿 v1 · 2026-09-13
> 定位：把「一份质控指标清单」变成**可配置、可追溯、可解释**的指标中台。127 条指标不写 127 段脚本，而是走「配置即代码」——指标口径写在 YAML 里，引擎统一编译成 SQL 执行，页面只认一套通用接口。

## 一、背景与定位

### 1.1 解决什么问题

质控指标（尤其是 ICU 重症质控上报口径）有三个固有难点，逐条写死在代码里会迅速失控：

1. **指标来源庞杂**：127 条指标来自多个口径来源（含 ARDS 专项 46 条），不同来源对同一事物的叫法、分母、统计单位都不一样，散落成 127 段 SQL 后无法统一维护。
2. **口径会变，且必须能回溯**：指标口径调整后，历史月份的值要能说明「当时是按哪一版口径算的」。没有版本概念就没法解释「为什么上月和这月的同一条指标不可比」。
3. **没数据源的指标不能消失**：18 条指标依赖尚未接入的源表（医嘱侧预防措施、床位/职工字典等），20 条口径待业务确认。这些如果不在页面上占位，看板就是残缺的、业务看不出「还差什么」。

### 1.2 核心设计原则

| 原则 | 落地方式 |
|---|---|
| **配置即代码** | 指标口径写在 `quality/metrics/*.yaml`，加一条指标只改配置、不写 SQL、不动接口、不动前端 |
| **不给出假 0** | 无数据源的指标返回 `null` 而非 `0`，页面显示「—」。0 和「不知道」是两件事，质控报表里混为一谈是事故 |
| **空壳也占位** | `implStatus=PLACEHOLDER/PENDING_SOURCE` 的指标照样进入看板，数值列为空，页面永远是完整的 127 行 |
| **口径可回溯** | 每个指标带 `version`，结果行落库时带 `expressionVersion` + `runId`，可反查「当时用哪版口径、哪批数据、扫了多少行」 |
| **四层血缘** | 批次 → 事实层 → 算子链/SQL → 患者级命中，逐层可下钻，任一数字都能追到人 |

### 1.3 与其它模块的关系

| 模块 | 关系 |
|---|---|
| ARDS 监测 | `fact_ards` 与 ARDS 监测页共用「ARDS 诊断 + 柏林分级」判定，可交叉验证 |
| 脓毒症集束化 | `fact_sepsis_bundle` 复用集束化模块的 1H/3H/6H 判定结果 |
| APACHE II 评分 | `fact_score_resource` 从评分记录取数，评分页与质控页口径一致 |
| DDD / MDRO / 出科统计 | 共享 ICU 只读库与「出科时间落在区间」的统计口径，便于同口径对比 |

## 三、分层设计（核心）

### 3.1 四层结构

```
① 数据源层  quality/sources.yaml
   └── 声明「本模块能用哪些表、表有什么字段」，与 ICU 真实库解耦
② 事实层 DWD quality/facts/*.yaml        10 个事实层
   └── 一次性把患者的散点数据铺平成宽表（如 fact_ards 一行一个 ARDS 患者，
       带 ards_mild / ards_moderate / prone / intubated / sex_male / age_num 等标签列）
③ 指标层 quality/metrics/*.yaml          127 条指标
   └── 每条只写「从哪个事实层、按什么条件、算分子/分母」，由 DSL 网关编译成 SQL
④ 血缘层 落库 6 张表
   └── run（批次）→ resource（事实层）→ trace（算子链+SQL）→ patient（命中患者）
```

各层的关系可以用一句话概括：**事实层负责「把患者变成一堆标签」，指标层负责「数标签」**。所以绝大多数指标（尤其 ARDS 专项那 46 条）都退化成 `COUNT(*) WHERE 若干标签列 = 1`，这也是为什么 127 条指标能靠 10 个事实层撑住。

### 3.2 为什么不是「每指标一段脚本」

| | 每指标一段 SQL | 本方案（DSL + 引擎） |
|---|---|---|
| 新增指标 | 写 SQL + 改接口 + 改前端 | 改一行 YAML |
| 口径变更 | 改代码 + 发版 | 改 YAML + 递增 version + 同步 |
| 无数据源指标 | 只能不写，页面缺失 | 标 `PENDING_SOURCE` 占位，页面可见 |
| 能否解释 | 靠人读 SQL | 算子链 + SQL + 扫描行数全落库 |
| 分母口径 | 各写各的，容易不一致 | 分母也是一条指标，可被复用（如 `quality_312` 就是 `quality_311` 的分母） |

## 四、指标口径

### 4.1 实现状态（`implStatus`）

| 状态 | 含义 | 数量 | 页面表现 |
|---|---|---|---|
| `IMPL` | 已实现，可算出值 | 85 | 正常显示数值 |
| `PENDING_SOURCE` | 口径明确，但源表未接入 | 18 | 数值列「—」，实现状态标「待接数据源」 |
| `PLACEHOLDER` | 口径本身待业务确认（如判定标准未定） | 20 | 数值列「—」，标「口径待定」 |
| `MANUAL` | 人工录入类 | 4 | 数值列「—」+「录入」按钮 |

> 合计 **127**（85 + 18 + 20 + 4）。这个分布本身就是交付物的一部分：覆盖率报告直接把它呈现成「按域承诺清单」，让业务方看到剩余 42 条的缺口在哪、卡在什么环节。

### 4.2 计算状态（`calcStatus`）

实现状态是**配置层**的静态承诺，计算状态是**运行期**的真实结果，两者不可混用：

| 状态 | 含义 |
|---|---|
| `OK` | 本期算出值（注意：值为 0 也是 OK，代表「确实一个都没有」） |
| `NO_DATA` | 口径成立但本周期无命中 |
| `NOT_CALC` | 本期未计算 |
| `PLACEHOLDER` / `PENDING_SOURCE` | 与实现状态对应，引擎直接跳过 |
| `MANUAL` | 待人工录入 |
| `ERROR` | 计算异常（SQL 报错等），需要关注 |

### 4.3 域分布（8 个域 / 127 条）

| 域 | 指标数 | 指标配置文件 |
|---|---|---|
| ARDS 专项 | 46 | `08_ards.yaml` |
| 脓毒症_感染性休克 | 27 | `02_sepsis.yaml` |
| 患者流转 | 11 | `01_patient_flow.yaml` |
| DVT 预防 | 11 | `04_dvt.yaml` |
| 导管_管路_院感 | 9 | `07_device.yaml` |
| 评估依从 | 8 | `06_assessment.yaml` |
| 抗菌药送检 | 8 | `03_abx_culture.yaml` |
| 评分_资源 | 7 | `05_score_resource.yaml` |
| **合计** | **127** | 8 个文件 |

### 4.4 口径版本

- 每个指标带 `version`（默认 1）。**改口径必须递增**，否则历史值的口径无法回溯。
- 结果行落库时记录 `expressionVersion` + `runId`，形成「值 ← 哪版口径 ← 哪批数据」的完整链条。
- 口径变更后同一指标前后不可比，页面上以「口径版本 vN」显式展示，避免误读趋势。

### 6.2 三层模型：原子项 ≠ 指标

这套系统里最容易搞混的一件事，必须先讲清楚：

| 层 | 是什么 | 在哪 | 规模 |
|---|---|---|---|
| **原子项** | 一个「多少人 / 多少天」的**量**，自身成不了率 | `quality_metric_def`（`index_code = quality_xxx`）+ `quality_metric_result` | 127 条 |
| **真指标** | **率** = 分子 ÷ 分母 × 放大系数 | `quality_count_rule`（同步自 ICU 侧） | 62 条（60 条上页） |
| 目标/预警 | 达标判定用的阈值 | `quality_count_rule.target_value` / `warning_value` | 待配置 |

举例：`ICU镇痛评估率 = quality_306（做了镇痛评估的人数）÷ quality_403（同期患者总数）× 100`；
`VAP发病率 = quality_24 ÷ quality_25 × 1000`（例/千呼吸机日）。

复用是常态而不是特例：`quality_449` 被 **17 条**指标当分母、`quality_403` 被 **13 条**当分母。
正因为如此「同期患者总数」这类口径只需在原子项上维护一次 —— 没有 rule 层，改一次口径要动 13 处。

**几个刻意的取舍：**

- **组装不重算 SQL**。分子分母的值已由引擎落在 `quality_metric_result`，`/rules` 只做一次除法。
- **原子项状态为 `PLACEHOLDER` 时不参与计算**。占位值是源表没接入时造出来的（如恒 0），
  拿它去除会得到一个看着像样、实则编造的率。质控宁可显示「—」，也不给临床一个假数。
  同理分母为 0 判 `NO_DATA` 而不是报错 —— 那是「本期没有分母人群」，不是故障。
- **达标方向刻意不推断**。质控既有「越高越好」（完成率、预防率）也有「越低越好」
  （发病率、病死率、重返率），而源表没有方向字段，凭名字猜会判反 —— **判反比不判更糟**。
  因此 `judge` 恒为 `NONE`，待业务明确后加 `target_direction` 字段再启用。
- **同步不覆盖本院已配置的目标值 / 预警值**，可放心重复点。

周期参数约定（`PeriodRange.of`）：`periodType ∈ MONTH / QUARTER / YEAR / CUSTOM`，`periodStart` 支持 `yyyy` / `yyyy-MM` / `yyyy-MM-dd` / `yyyy-MM-dd HH:mm:ss`；两者都不传时后端默认取「上个月」（与「出院患者看上月」的统计习惯一致）。周期区间为**左闭右开**。

### 6.1 单指标重算与异步批次

整批 127 条要跑几分钟。真实使用里最常见的场景是**只改了一条指标的口径，只想看这一条**，
为此不必等全量跑完 —— 这两个能力就是为此加的。

| | 单指标重算 | 整批异步重算 |
|---|---|---|
| 入口 | `POST /recalc/metric?code=` | `POST /recalc?async=true` → `GET /run?runId=` |
| 代价 | 只重建该指标依赖的**那一张**事实表 | 全部 127 条 |
| 返回 | 秒级结果，含该科室这一行结果 | 立即返回 `runId`，需轮询到终态 |
| 页面反馈 | 行级 loading，成功后**就地替换这一行** | 2s 轮询 + 进度条（容错 5 次，30 分钟上限） |

几个实现上的取舍：

- **幂等**：单指标重算会先 `deleteByMetricPeriod(code, periodType, start)`，
  把该指标在本周期下的**所有科室行一并覆盖**，避免新旧结果混杂。
- **互斥用的是 `tryLock` 而不是 `lock`**：批算期间点单指标会**立即返回 BUSY**
  （"已有计算任务在执行，请稍候再试"），而不是让请求排队到浏览器超时。
  让用户马上知道在忙，比让他盯着转圈好。
- **进度有两套来源**：实时计数（`runId → RunProgress`）只在内存 `ConcurrentHashMap`，
  每完成一条就写库太重；而**结论**（`status` / `ok` / `fail` / `placeholder` / `durationMs`）
  仍然落在 `quality_calc_run` 表。`getRun` 先读表，内存取不到实时进度时（例如服务刚重启）
  退回用表里的 `status` 判断终态 —— 此时**进度条会显得不准，但不会卡死**。
  单实例部署下不受影响；若将来多实例，需保证同一 `runId` 的轮询落到同一实例。
- **轮询的容错是刻意的**：间隔 2s，单次失败不中断（后端重启、网络抖动都算常态），
  **连续 5 次失败**才判定真失败，另有 30 分钟上限兜底 ——
  宁可让用户多等一会儿，也不要因为一次抖动就把正在跑的批次判死。
- `GET /run` 返回里 `running=false` 即终态，此时 `ok` / `fail` / `placeholder` / `durationMs` 才是结论。

**交互规则**

| 规则 | 说明 |
|---|---|
| 列顺序 | 指标编号 + 指标名称**左固定**，全年合计 / 月均 / 极值月**右固定**，中间 12 个月横向滚动 |
| 值类型聚合口径 | **率类按「分子分母先汇总再重算」得加权值，数类直接求和**——绝不能对 12 个月的率做算术平均，那是典型的错算法 |
| 极值月高亮 | 年内最高月标红、最低月标绿，单元格级着色，一眼看出波动 |
| 空行弱化 | 全 12 月无值的指标整行灰化，不干扰有数据的行 |
| 只看有数据 | 默认关闭（保持 127 行完整），需要聚焦时再开 |
| 年度趋势 | 指标下拉按域分组 + 可搜索，避免 127 条平铺 |
| 重建与导出的关系 | 导入导出依赖汇总宽表，所以按钮顺序是「重建汇总 → 导出 Excel」，且无数据时导出按钮禁用 |

**月度汇总数据的产生链路（页面要能解释清楚）**

```
看板页「触发计算」(MONTH)  →  quality_metric_result（月结果）
        ↓ POST /monthly/rebuild
quality_monthly_report（1-12 月折叠宽表，幂等先删后建）
        ↓ GET /monthly、GET /export
页面宽表 / xlsx（3 sheet）
```

> 所以「月度汇总为空」的两种成因要在页面上区分：**结果表就没有月数据**（先去触发计算）vs **有月数据但没重建汇总**（点重建）。

### 7.4 两页共用的约定

| 约定 | 说明 |
|---|---|
| 周期参数 | 按季传 `yyyy-MM`（如 `2026-07` 表示 Q3），后端 `PeriodRange.of` 自动推区间 |
| 科室 | 传空 = 全院（`ALL`），不传 `departCode` 与传空等价 |
| 外链上下文 | 两页均通过 `/entry/{pageCode}` 接收外层重症系统参数，独立访问时用页面自身筛选栏 |
| 错误提示 | 「触发计算/同步字典/重建/录入」这类带副作用的操作由页面统一弹错误（带操作上下文），避免与拦截器弹窗重复 |
| 二进制响应 | 导出走裸 `axios`（`responseType=blob`）并手动注入外链鉴权头，绕开统一拦截器的 `Result` 解包 |

## 八、配置项与指标维护

### 8.1 三层配置

| 层 | 路径 | 作用 |
|---|---|---|
| 数据源 | `quality/sources.yaml` | 声明可用表与字段 |
| 事实层 | `quality/facts/{patient,clinical,support}.yaml` | 10 个 DWD 宽表定义 |
| 指标 | `quality/metrics/*.yaml` | 127 条指标口径（8 个文件按域拆分） |

指标行示例：

```yaml
- {code: quality_420, name: "收治的ARDS患者数", domain: ARDS专项, fact: fact_ards,
   unit: "人", valueType: COUNT, where: "ards = 1", dims: [depart_code],
   version: 1, sortNo: 57, remark: "ARDS 人群识别基于诊断（含 ARDS / 急性呼吸窘迫）"}
```

### 8.2 新增 / 编辑 / 删除

| 操作 | 步骤 | 是否要发版 |
|---|---|---|
| **新增** | YAML 加一行（`code`/`name`/`domain`/`fact`/`where` 或 `numerator`+`denominator`）→ 调「同步字典」 | 否 |
| **编辑口径** | 改 YAML 那一行 → **递增 `version`** → 同步 | 否 |
| **删除** | 从 YAML 移除 → 同步 | 否 |

**删除是「置停用」而非物理删除**：同步时对「库里启用、配置里已不存在」的指标执行 `disableByCode`（`status=0`），原因是 `quality_metric_result` 的历史结果要靠字典回溯，物理删会留下孤儿记录。字典表只读 `status=1`，所以停用后立刻从看板消失，但历史值仍可查。

一个安全兜底：**指标配置加载为空时（如 YAML 解析失败）同步会提前返回，不会把全部指标误停用**。

### 8.3 生效方式

- 应用启动时通过 `ApplicationReadyEvent` **自动同步一次**，所以首次部署即可看到完整字典。
- 运行期改完 YAML 不必重启，调一次 `POST /api/quality/sync-index`（页面「同步字典」按钮）热生效。

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | 42 条指标（18 待接源 + 20 口径待定 + 4 人工）暂不出数 | 覆盖率不完整，但页面已如实呈现缺口 | 按覆盖率报告逐域销项；3 张缺失源表是最大阻塞 |

| 8 | **3 条原子项口径待确认**（`quality_15` / `quality_30` / `quality_31`） | 涉及这三条的指标值可能有**数量级偏差**，其余 59 条不受影响 | 这三条在我们 YAML 里自带百分比语义（`AVG` / `RATE unit=%`），但 ICU 侧又拿它们与另一个原子项相除 —— 源表存的究竟是「率」还是「率之和」未确认。**当前按公式照算 + 页面打「口径待确认」角标**，不阻塞其余指标；确认后去掉 `QualityCountRuleService.PENDING_CONFIRM_CODES` 中的条目即可 |
