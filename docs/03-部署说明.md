# 部署说明

## 1. 环境依赖

| 组件 | 版本 | 说明 |
|---|---|---|
| JDK | 8+（本机编译） | 服务器运行用 Docker JRE8 镜像 |
| Maven | 3.6+ | 构建后端 |
| Node.js | 18/20 | 构建前端 |
| Docker / docker-compose | 任意较新版本 | 生产部署 |
| 达梦数据库 DM8 | 服务器上 ICU 系统所在实例 | 主库（医生决策系统自有）+ ICU 只读库 |

| MySQL 8.0+ / MariaDB 10.5+ | 替代数据库（可选） | 院方 ICU 库为 MySQL/MariaDB 系时选用，脚本为 `sql/mysql/` + `install-mariadb-debian.sh` |

>
> **两套数据库、两套脚本**：本节是**达梦 DM8**（`sql/` + `install.sh`）。MySQL / MariaDB 走另一套
> `sql/mysql/` + `install-mariadb-debian.sh`（连接参数写在 `conf/db.conf`，Spring profile 由脚本自动切到 `mariadb`/`mysql`），

> `install.sh` 的**全量初始化**按 `FULL_SQL` 数组顺序执行 `00`~`23`（三个初始化通道均已纳入；JDBC 通道额外带 `03` / `05`）。
> ⚠️ 若为**已初始化过的老库**（检测到 `zing_page_config` 已存在），`install.sh` 会跳过全量建库，改为自动套用 `INCREMENTAL_SQL`（`09`~`23`，全部幂等），并在结束后**显式复查关键列**（`quality_metric_result.value_source` / `operator` / `manual_note`、`quality_count_rule.target_direction`），缺列直接抛错提示。因此老库升级通常**无需手动执行 SQL**。两个例外：
> - `06_abx_drug_dict.sql` 为一次性脚本（裸 `CREATE TABLE`），不在增量清单内 —— 若从未执行过需**手动执行一次**（重复执行会报表已存在，可先 `DROP TABLE` 或忽略该报错）；
> - `11_quality_count_rule.sql` 建表后，需在看板点一次「同步指标规则」从 ICU 侧灌数。
>
> ⚠️ **新增 SQL 脚本必须同步登记到 `install.sh` 的三个数组**（`FULL_SQL` / `FULL_SQL_JDBC` / `INCREMENTAL_SQL`，数组顺序 = 依赖顺序）。只放进 `sql/` 目录而不登记 → 老库升级不补表 → 页面 500。`22_ards_prone_config.sql` 就是这么踩的：参数设置 →「ARDS 数据映射」点「一键从内置生成」报 `无效的表或视图名[ards_prone_config]`。
>
> 以下为**自动增量未命中**（三条通道都不可用）时的症状，此时才需按上表手动逐个执行：
> ⚠️ 漏执行 `06` 不会导致页面 500，但 `AbxDrugRecognizer` 词库刷新会持续告警 `无效的表或视图名[zing_abx_drug_dict]`，抗菌药识别降级为关键词匹配。
> ⚠️ 漏执行 `09` 会同时导致两个后果：**质控看板 / 月度汇总页直接报错**（`quality_index` 等表不存在），且 `quality-board` / `quality-monthly` 未登记进 `zing_page_config` → `/entry/...` 外链被判定为未注册页面而拒绝。
> ⚠️ 漏执行 `10` 会同时导致两个后果：**配置页保存时报「无效的表或视图名[quality_metric_def]」**，且 `quality-config` 未登记 → `/entry/quality-config` 外链返回 `{"code":404,"message":"未注册的页面：quality-config"}`。
> ⚠️ 漏执行 `11` 时看板「质控指标」页会提示「还没有指标规则」（表不存在，后端查询报错被吞成空列表）。**只建表也不够** —— 该脚本刻意不含同步语句（跨 schema 引用 ICU 库，新环境下会拖垮整条初始化链），需**建表后在看板右上角点一次「同步指标规则」**从 ICU 侧灌数，之后 ICU 侧规则有增删再点即可（幂等）。

> `zing_icu_db_prod` 为 ICU 系统既有模式，医生决策系统**只读**，**不要**在此初始化脚本中创建/修改。
> 医生决策系统统一用 `SYSDBA` 连接（与 ICU 系统访问方式一致），通过显式模式前缀访问 `zing_doctor_db_prod`、`zing_icu_db_prod` 两个模式。

## 6. ICU 表结构接入（SQL 实现已就绪）

已基于 ICU 系统真实表结构实现 `SqlIcuPatientServiceImpl`（`@DS("icu")` 只读查询 zing_icu_db_prod），切换方式：

1. 在 ICU 数据源连接可用的前提下，设置 `zing.doctor.icu-data-provider=sql`（或环境变量 `ICU_DATA_PROVIDER=sql`）。
2. 重启后端，列表/评估数据改为真实 ICU 数据；`mock` 实现通过 `@ConditionalOnProperty` 自动停用。

### 表结构映射（第一维度）

| ICU 表 | 用途 | 取数要点 |
|---|---|---|
| `patient_info` | 患者信息/过敏史/体重/脓毒性休克/多耐药标记 | 在科 `is_in_depart=1`、未删除；`is_sepsis_shock` 休克；`multidrug_resistant_bacteria` 字典 1MRSA 2VRE 3CRE 4CR-AB 5MDR/PDR-PA |
| `patient_info_diagnosis` | 感染类型推断、真菌风险 | `diag_name` 关键词匹配（脓毒/肺炎/腹腔/血流/尿路/真菌） |
| `patient_info_lis_item` | 检验指标 PCT/WBC/CRP/肌酐/乳酸 + **微生物培养/药敏结果** | 检验指标按 `lis_item_name` 名称匹配取最新；微生物结果：`lis_item_name` 含 培养/药敏/涂片/镜检/菌 → `lis_item_result` 即**检出菌名或药敏结论**，按住院号查询 |
| `patient_observe_module_item_record` + `config_observe_item` | 体温 | 观察项记录 join 项目配置，`item_name LIKE '%体温%'` 或 `sign_code` 匹配 |
| `patient_advice_execute` | 当前抗菌药医嘱 | 执行中/未执行医嘱按抗菌药关键词过滤，取最早开始时间 |

### 微生物培养/药敏数据说明

- 数据位置：`patient_info_lis`（报告头，含标本类型 `lis_short_name`、报告名 `lis_name`、检查时间）与 `patient_info_lis_item`（结果明细）。
- 明细结果形态（实测样例）：`lis_item_name='细菌培养+药敏'` → `lis_item_result='鲍曼不动杆菌'`（结果值即菌名）；`'细菌（镜检）'`→`'2+'`；`'细菌培养+药敏(厌氧瓶)'`→`'奇异变形杆菌'`。
- 关联键：表结构上 `patient_info_lis.lis_code = patient_info_lis_item.lis_code`；实现按**住院号 + 微生物关键词**直接查明细（不依赖报告头关联，规避导出子集不一致），`LEFT JOIN patient_info_lis` 尽力带出标本类型。
- 用途：培养菌名驱动 `pastCultures`（既往培养）与 MDR/MRSA/真菌风险增强（如菌名含 MRSA/ESBL/鲍曼/铜绿/念珠菌等自动提升风险标记）。
- 药敏结论行（result 为 S/I/R 或 敏感/中介/耐药）解析为「标本 药敏：药物 → 结论」。

## 7. 交付包命名规范

统一格式（`<版本>` 取自 `pom.xml` 的 `<version>`，`<yyyyMMdd>` 为打包当天日期）：

```
zing-doctor-<版本>-<形态>-<yyyyMMdd>.tar.gz
zing-doctor-<版本>-<形态>-<yyyyMMdd>.zip
```

| 段 | 取值 | 说明 |
|---|---|---|
| `zing-doctor` | 固定 | 取自 `pom.xml` 的 `artifactId` / `<finalName>` |
| `<版本>` | 如 `1.0.0` | 与 `pom.xml` 的 `<version>` 保持一致；热修可加后缀，如 `1.0.0-hotfix1` |
| `<形态>` | `full` / `runtime` / `runtime-slim` | 见下表「形态对照」 |
| `<yyyyMMdd>` | 如 `20260911` | 打包当天日期（本地时区） |
| 扩展名 | `.tar.gz`（首选）/ `.zip` | Linux 部署用 `.tar.gz`（保留权限位与 UTF-8 文件名）；`.zip` 供 Windows 传输/解压 |

### 形态对照

| 形态 | 含后端源码 | 含 `tools/docker-compose` 离线二进制 | 适用场景 | 体积参考 |
|---|---|---|---|---|
| `full` | 是 | 是 | 需在服务器重建 / 归档；内网且无 compose 时 | ~62 MB |
| `runtime` | 否 | 是 | 纯部署；服务器**无** `docker compose` 且无外网 | ~62 MB |
| `runtime-slim` | 否 | 否 | 纯部署；服务器**自带** `docker compose`（推荐） | ~29 MB |

三种形态共存内容：`install.sh`、`docker-compose.yml`、`Dockerfile`、`app/zing-doctor.jar`、`frontend/dist/`、`frontend/nginx.conf`、`lib/`、`sql/`、部署必需文档（`docs/02-外链传参规范.md`、`docs/03-部署说明.md`、`docs/04-安装部署手册.md`）、`tools/db-init`（只含编译产物 `.class`）、`DEPLOY.md`、`DATABASE-CHANGES.md`。

> **内容白名单（外发安全）**：打包脚本按白名单组装，**源码与设计资料一律不进包** —— 后端/前端源码、`DbInit.java`、产品设计文档（05~17）、`docs/ards-prone` 原型、`docs/quality-board-redesign` 设计稿、sourcemap、`node_modules` / `target` / `.git` 全部剔除。
> 需要内部归档时加 `-KeepDocs`（额外带 `docs/` 全部与 `README.md`）。打完包脚本会跑一次**出库自检**，命中黑名单（`.java` / `.map` / `*.vue` / `pom.xml` / `src/` …）直接中止。

- `full` 额外含：`src/`、`pom.xml`、`frontend/src` 及其开发配置（`package.json`、`vite.config.js` 等）。
- `runtime` / `runtime-slim` 一律剔除：源码与开发配置、`target/`、`logs/`、`node_modules/`。

### 打包执行要点

1. **版本号必须与 `pom.xml` 的 `<version>` 一致**，避免出现「包名版本 ≠ 实际代码版本」。
2. 打包前先重建产物，确保包内是最新构建：
   ```bash
   mvn clean package                  # 后端 → 覆盖 app/zing-doctor.jar
   cd frontend && npm run build       # 前端 → 生成 frontend/dist
   ```
3. 压缩包内顶层目录固定为 `zing-doctor/`，解压后可直接 `bash install.sh`。
4. 同一天多次打包**直接覆盖同名文件**（以最后一次为准），不引入 `-v1/-v2` 之类后缀，避免线上取错包。
5. 交付前自检：包内含 `app/zing-doctor.jar` 与 `frontend/dist/index.html`；`runtime*` 形态内**不含** `src/`、`pom.xml`、`node_modules`。
6. `install.sh` 默认按「服务器自带 `docker compose`」工作；若目标服务器缺失，请改用 `runtime` 形态（包内自带离线 compose 二进制）。

### 打包命令与脱敏

```powershell
# Windows（PowerShell）
.\tools\build-delivery.ps1 -Lite                  # 精简包：出厂口令，内部 / 现场直接用
.\tools\build-delivery.ps1 -Build -Lite           # 先 mvn package + vite build 再打包
.\tools\build-delivery.ps1 -Build -Lite -Sanitize # 外发包：口令密钥置为 CHANGE_ME
.\tools\build-delivery.ps1 -Build -KeepDocs       # 内部归档：额外带 docs/ 全部与 README.md
```

| 参数 | 作用 |
|---|---|
| `-Lite` | 不含离线 `docker-compose` 二进制（服务器自带 compose 时用，省 80+ MB） |
| `-Build` | 打包前先构建后端 jar 与前端 dist |
| `-KeepDocs` | 额外打进 `docs/` 全部与 `README.md`（**仅内部交付**） |
| `-Sanitize` | 脱敏：包名加 `-sanitized`，并把出厂口令/密钥置为 `CHANGE_ME` |

**`-Sanitize` 做了什么**（外发给院方前必做）：

- `docker-compose.yml` 的 `DOCTOR_PASSWORD` / `EXTERNAL_LINK_SECRET` / `ICU_LINK_TOKEN` → `CHANGE_ME`
- jar 内 `BOOT-INF/classes/application.yml` 的 `password` / `secret` / `icu-token` / `jwt-secret` / `admin-password` 默认值 → `CHANGE_ME`（host/port 等非敏感默认值保留，改了现场会连不上）

⚠️ 脱敏包**必须由部署方先填真实口令**才能用：`install.sh` 从 `docker-compose.yml` 取 `DOCTOR_PASSWORD` 做数据库初始化，后端直连模式也读 jar 内默认口令；不填则初始化与连库都会失败。也可改注入环境变量：`DM_DOCTOR_PASSWORD` / `DM_ICU_PASSWORD` / `EXTERNAL_LINK_SECRET` / `AUTH_JWT_SECRET` / `ADMIN_PASSWORD`。
